## many-ai-cli について

自作で [many-ai-cli](https://github.com/ishizakahiroshi/many-ai-cli) という AI ツール向けの Web ダッシュボードを作っています。複数の AI コーディング CLI を並列で走らせ、承認をブラウザ 1 タブに集約。スマホからでも。

- 何ができるかの紹介ページ: https://ishizakahiroshi.com/work.html?id=many-ai-cli
- リポジトリ（Star をいただけると励みになります）: https://github.com/ishizakahiroshi/many-ai-cli

同じ悩みを持っている方は、下記で入ります。

```bash
npm i -g many-ai-cli
```

入れたら 1 回だけ `many-ai-cli setup` を実行します。これがデスクトップとスタートアップにショートカットを作り、設定ディレクトリ `~/.many-ai-cli/` を用意します。PATH に載らない場合は `npm bin -g` の出力を PATH に足してください。

起動後の見え方は OS で違います。

Windows では、`setup` が置いた「MANY-AI-CLI」のショートカットから起動すると通知領域にトレイアイコンが常駐します。サインイン時にも自動で起動します。止めるときはトレイアイコンのメニューから終了します。

macOS と Linux にはトレイがありません。ターミナルから `many-ai-cli serve` で Hub を立ち上げ、`many-ai-cli stop` で止めます。

全 OS 共通で、`many-ai-cli claude` のように provider 名をサブコマンドにすると、Hub が動いていなければ自動で起動してからその CLI をラップして立ち上げます。

起動したら `http://127.0.0.1:47777/?token=...` がブラウザで開くので、そこがダッシュボードです。

実機で確認できているのは Windows のローカル Hub と Windows 統合ランチャーで、ネイティブ Linux とネイティブ macOS はまだ全面的な検証ができていません。README にもそう書いています。

## この記事の読み方

3 つの層は独立して読めます。興味のあるところだけ拾ってください。

1. **契約を積む層**: 1 つの AI CLI に、自分が払っている複数の月額契約をぶら下げる
2. **引き継ぐ層**: 詰まったセッションの状態を次のセッションへ渡す
3. **任せる層**: 指揮者 AI が子 AI を回す範囲を広げる

最後に、その他の変更とセキュリティ修正、それとリリース作業で踏んだ失敗を置いています。

# 第 1 層: 1 つの CLI に、契約を 2 本ぶら下げる

## 「同じ CLI を 2 つ動かす」だけが、どうしてもできなかった

ダッシュボードは前から Claude Code、Codex CLI、GitHub Copilot CLI、Cursor Agent CLI、Grok Build CLI、opencode を横に並べられました。違う CLI を同時に動かすのは最初からできる。

できなかったのは、**同じ CLI を 2 つ、別々の月額プランで動かす**ことです。

公式 CLI はどれも「既定のログイン 1 つ」を覚える作りになっています。`claude` を 2 つ立ち上げても、両方とも同じアカウントを見にいく。片方が上限に当たれば、もう片方も一緒に止まります。

契約自体は複数持っている。でもツール側にそれを使う口が無い。ここが v0.8.0 で最初に埋めた穴です。

![契約プロファイルは設定ディレクトリを env で切っているだけ](https://raw.githubusercontent.com/ishizakahiroshi/qiita-content/main/public/images/03_2026-09-09_many-ai-cli-v080_qiita-fig1.png)

図のとおり、やっていることは 1 つだけです。公式 CLI が設定ディレクトリの場所を環境変数で選べるようになっているので、その環境変数を起動時に差し替える。それだけで別のログインとして動きます。

## 設計の不変条件を先に固定した

この機能で怖いのは、実装より先に「そのうち token を持ちたくなる」ことでした。残量を見て自動で切り替えたい、ログイン状態をまとめて管理したい。どれも便利そうに見えて、認証情報を自分で抱えることになります。

なので先に不変条件を 3 つ決めて、**コードのパッケージ doc とテストに書き込みました**。

```go
// internal/subscription/adapter.go のパッケージ doc（要約）
//
// 複数サブスクリプションは「設定ディレクトリを env で切る」だけで実現する。
// many-ai-cli は token を読まない・書かない・解釈しない・保存しない。
```

テストは 3 本です。

- `TestLiveSessionAuthIsNeverSwapped`: 走っているセッションの認証を後から差し替えない
- `TestSeedIsAdditiveOnly`: profile へ持ち込む設定は追記だけ。既存を書き換えない
- `TestSeedNeverCarriesCredentials`: credential を profile へ運ばない

3 つ目が特に効きます。「既定の設定をプロファイルへコピーする」機能を作ると、その勢いで認証ファイルまでコピーしたくなる。テストが落ちるようにしておくと、その手が止まります。

## profile の実体

1 プロファイル = 1 ディレクトリです。

```
~/.many-ai-cli/subscriptions/
  claude/
    work/        ← CLAUDE_CONFIG_DIR をここに向ける
    private/
  codex/
    main/        ← CODEX_HOME をここに向ける
  grok/
    main/        ← GROK_HOME
  opencode/
    main/        ← XDG_DATA_HOME
```

`config.yaml` に入るのは、プロファイルの id、表示名、プラン名、有効フラグの 4 つだけです。token は 1 バイトも入りません。

ログインは公式 CLI にやらせます。ダッシュボードの「ログイン」ボタンを押すと、そのディレクトリを指した状態で `claude auth login` や `codex login` を短命セッションとして起動します。ベンダーの通常のサインイン画面が出て、認証情報はそのディレクトリの中に公式 CLI が置く。こちらは触りません。

対応状況は provider で割れます。

| Provider | 使う環境変数 | 対応 |
|---|---|---|
| Claude Code | `CLAUDE_CONFIG_DIR` | 対応 |
| Codex CLI | `CODEX_HOME` | 対応 |
| Grok Build CLI | `GROK_HOME` | 対応 |
| opencode | `XDG_DATA_HOME` | 対応 |
| GitHub Copilot CLI |: | 未対応 |
| Cursor Agent CLI |: | 未対応 |
| Command Code |: | 未対応 |

Copilot は token を OS の資格情報ストアに置きます。`COPILOT_HOME` で設定は移せますが、**ログインは移りません**。Cursor は `~/.cursor/cli-config.json` に置いていて、これを移す環境変数がありません。

この 2 つは「半分動く」状態にせず、プロファイルの登録自体を拒否しました。半分動くと、2 つのセッションが黙って 1 つのアカウントを共有します。それはツールの都合ではなく、利用規約の問題になります。

## auto は round-robin だけ。残量を見ない

プロファイルが 2 つ以上あるとき、spawn フォームで `auto` を選べます。ここで意図的に外した機能があります。

**残量を見て、空いている契約へ自動で乗り換えることをしません。**

やっているのは spawn したときの round-robin だけで、選ばれたプロファイルを記録します。それだけ。

これも設計の不変条件として固定しました。

```go
// internal/hub/subscription.go の pickAutoSubscription 冒頭（要約）
//
// auto 選択は spawn 時の round-robin だけ。
// 残量を見て自動で別契約へ乗り換えない。
```

テストは `TestAutoSubscriptionNeverConsultsUsage` です。usage の取得経路をこの関数から呼んだら落ちます。

理由は 2 つあります。1 つは、上限に当たった瞬間に別契約へ移す挙動が、ベンダーから見て何に見えるかを自分で判断できないこと。もう 1 つは、乗り換えの判断をツールが黙ってやると、利用者が「どの契約でどれだけ使ったか」を追えなくなることです。

複数契約を積むのは、API キーを束ねて安くする仕組みではありません。**すでに払っている月額の枠へ、すでに走らせているセッションを割り振るだけ**です。ここを曖昧にすると、機能の性格が変わります。

## 2 本目を足す前に、同意ゲートを出す

とはいえ、複数契約を積むこと自体の注意点は README にしか書いていませんでした。画面側は無言。

同じ性質のリスクに対して、モバイル接続のウィザードにはすでに同意ゲートがあります。そこだけ扱いが揃っていなかったので、v0.8.0 で足しました。

出るのは、同じ provider に **2 本目のプロファイルを足す直前の 1 回だけ**です。1 本目では出ません。spawn フォームの契約セレクタが `profiles.length >= 2` で初めて現れるのと同じ境界に合わせました。

文面は README にある表現だけで組んでいます。書いていないのは「規約違反ではありません」という保証で、書いているのは次の 4 点です。

- 複数のプランを保有すること自体は禁じられていない
- 上限に達したあとの乗り換えは別の話で、判定はベンダー側であり返金もない
- 公式の有償手段（上位プラン・追加クレジット）が先である
- many-ai-cli は残量を見て自動で切り替えない

同意は `localStorage` に持ちます。証跡を作るためではなく、利用者が 1 度は読んだ状態を作るためです。

![2 つの契約を並べて走らせている机の風景](https://raw.githubusercontent.com/ishizakahiroshi/qiita-content/main/public/images/04_2026-09-09_many-ai-cli-v080_illustration-two-plans.png)

契約を積めるようになると、次に見たくなるのは「今どっちがどれだけ残っているか」です。

## 残量は「取りにいく」のではなく「落ちているものを読む」

Usage メニューは、積んだ契約の内訳を見るための画面です。独立した機能ではありません。

ここで一番の判断は、**残量を問い合わせて取りにいく経路を作らなかった**ことです。

読んでいるのは、CLI が自分のためにローカルへ書いているファイルだけです。

- Claude: 5 時間枠と 7 日枠。走っているセッションが何も報告していないときだけ、1 ターンだけの probe をその場で投げる
- Codex: ローカルの rollout JSONL
- Grok: ローカルの課金ログ
- Copilot / Cursor / opencode: ベンダーのページへのリンクだけ

数字はメニューを開いたときに読みます。定期ポーリングはしません。

![残量ソースを provider ごとの switch ではなく 1 本の表で持つ](https://raw.githubusercontent.com/ishizakahiroshi/qiita-content/main/public/images/05_2026-09-09_many-ai-cli-v080_qiita-fig2.png)

図のとおり、provider ごとの分岐を複数の switch 文へ手書きするのをやめて、`internal/subscription/usage_source.go` の 1 本の表に寄せました。provider を足すときに触るのは、その表の 1 行と、その provider 用のファイルパーサだけです。provider の id を比較している場所を全部探して回る作業が消えます。

この整理のついでに、Cursor Agent が残量をローカルに持っていないかを実際に見にいきました。Free tier で確認した範囲では、`about` にも `status` にも残量の欄が無く、設定ディレクトリの下にもそれらしいファイルがありません。**検知できないものは「未検知」として表に書く**ほうが、無理に推定するより後で困りません。

## ログインしたら、セッション一覧に `dist` という箱が生えた

この層で踏んだ細かいバグを 1 つ書いておきます。

契約のログインボタンは、ベンダーの CLI を Hub のプロセス作業ディレクトリで起動していました。Hub 自体をビルド出力のフォルダから立ち上げていると、そのディレクトリ名は `dist` です。結果、セッション一覧に `dist` という名前のプロジェクトグループが生えました。

さらに `grok login` は「サインインしました」と表示したあとも待機状態のまま残り、カードが消えませんでした。死んだセッションの自動片付けは 24 時間なので、丸一日居座ります。

直したのは 2 点です。ログインは `~/.many-ai-cli/subscription-login` で走らせるようにして、ベンダー CLI が終了するかサインイン成功の行を出した時点で Hub 側がセッションを閉じるようにしました。

# 第 2 層: 詰まったセッションを、次へ渡す

## セッションが死ぬとき、何も残らない

長く走らせていると、セッションはいろいろな理由で使えなくなります。契約の枠を使い切る。文脈が伸びきって噛み合わなくなる。CLI 自体が固まる。

そのとき困るのは、**そこまでに何をやったかが、そのセッションの中にしか無い**ことです。

新しいセッションを立てて、また同じ説明を書く。plan の md を渡してもよいけれど、直前にどこまで進んだかは md には書かれていない。この往復が地味に重い。

v0.8.0 で足したのは、この往復を短くするための「引き継ぎ看板」です。

## まず器から。入れてよいものを型で決める

最初のコミットで入れたのは器だけです。動いているセッションからは、まだ何も書きません。

置き場所は `~/.many-ai-cli/handoff/s<セッションid>.jsonl` で、追記だけします。

設計で一番こだわったのは、**何を入れてよいかを Go の型で決めた**ことです。

```go
// internal/handoff/handoff.go の冒頭コメント（要約）
//
// 入れてよいものだけを型で受ける。それ以外は入れる口を作らない。
// 伏字化は最後の網であって、最初の守りではない。
```

つまり、PTY のトランスクリプト・ファイルの中身・diff・環境変数を**入れられるフィールドが存在しません**。後から自由テキストを走査して危なそうな文字列を伏せる、という作りにしていない。自由テキストのフィールドは 1 つだけあって、それは書き込む前に既存の秘密マスク処理を通します。

テストは `internal/handoff/handoff_test.go` の allowlist フィールド固定テストです。型にフィールドを足すとテストが落ちます。落ちたら「そのフィールドは本当に看板へ入れてよいか」を考える、という運用にしました。

![引き継ぎ看板に入るもの、入れる口すら無いもの](https://raw.githubusercontent.com/ishizakahiroshi/qiita-content/main/public/images/06_2026-09-09_many-ai-cli-v080_qiita-fig3.png)

図の左が看板に入るもの、右が入れる口を作っていないものです。右側を「伏字にする」ではなく「フィールドが無い」にしているところが違いです。

保持は既定 14 日（`handoff.retention_days`）で、Hub の既存の定期メンテナンス掃除が消します。この掃除は **機能を無効にしていても走ります**。`handoff.enabled: false` は新規の書き込みを止めるだけで、すでに書かれたものは放置しない、という分け方です。

`many-ai-cli doctor` は看板ディレクトリのファイル数といちばん古いファイルの経過日数を報告します。**利用者のディスクへ書く機能は、次回起動時の回収まで設計する**というのは、このリポジトリで前から持っているルールです。

## 「終わったこと」だけでは引き継げない

器ができて次に気づいたのは、記録するのが完了報告だけだと足りない、ということでした。

many-ai-cli には前から、AI が作業を終えたときに出す完了サマリーのマーカーがあります。そこに何をしたかは書かれる。でも**次に何をすればいいかは書かれない**。

そこで、完了マーカーの書式に任意の 2 行を足しました。

```
次: <次にやること 1 行>
未検証: <確かめていない前提 1 行>
```

この 2 行があるときだけ、Hub は `kind=intent` の行として別に書きます。無くても何も変わりません。必須にしていないのは、書式を厳しくすると AI 側が守れずに全部落ちるからです。

「終わったこと」と「これからやること」を別の種類として持つと、後続のセッションが読む順番が決まります。まず intent を読み、必要なら完了サマリーを遡る。

## 毎ターン要約は作ったが、既定では止めてある

もう一段細かい記録もできるようにしました。設定 → セッション → 「引き継ぎの記録」で選べます。

- `done-only`（既定）: 完了サマリーと intent 行だけ
- `turn-summary`: 毎ターン、セッション自身に 1 行の要約を書かせる

`turn-summary` は、Git タブの AI コミットメッセージと同じ仕組み（プロンプトを注入してマーカーで回収する）を使っています。仕組みは同じですが、**毎ターン、そのセッション自身のトークンを使います**。

だから既定は off です。「あると便利」と「常時 on にしてよい」は別だと思っていて、後者の基準はトークンを毎ターン払う価値があるかどうかにしました。

## PTY を見ていても、止まっているかは分からない

引き継ぎたくなる場面の代表が「詰まっている」ときです。ところが、詰まっているかどうかの判定が今まで雑でした。

v0.7.0 までは、5 分を超えたセッションに「Long-running」のバッジを 1 つ出して、そのあとは何時間経っても同じ表示でした。重いターンと固まったターンが、待っているあいだずっと同じ顔をしている。

v0.8.0 でバッジに経過時間を入れて（`⚠ Long-running 38m`）、15 分で段を上げるようにしました。ここまでは表示の話です。

本題はここからで、**PTY の出力だけを見ていても、止まっているかは判定できません**。

Codex は `Working (36m 09s)` のカウンタを 1 秒ごとに描き直します。端末のストリームから見ると、30 分何も進んでいないセッションも「ずっと何か出力している」ように見える。

![PTY では動いて見える。transcript は伸びていない](https://raw.githubusercontent.com/ishizakahiroshi/qiita-content/main/public/images/07_2026-09-09_many-ai-cli-v080_qiita-fig4.png)

そこで見る対象を変えました。CLI が自分で書いているトランスクリプト（Codex の rollout JSONL、Claude Code のトランスクリプト）は、**ターンが実際に進んだときにしか伸びません**。

そのファイルが 10 分伸びなかったら、バッジを「Not progressing」に切り替えます。

読んでいるのはファイルのサイズだけで、中身は読みません。トランスクリプトにはプロンプトもソースの断片も認証情報も入りうるので、そこは開かない。サイズが増えたか増えていないかだけで足ります（`internal/hub/transcript_stall.go`）。

## 看板から、次のセッションを起こす

ここまでで「記録が残る」「詰まったのが分かる」が揃いました。最後が引き渡しです。

セッションの看板から、1 画面ぶんの Markdown を組み立てます。中身は、そのセッションの識別情報、直近の完了サマリー、直近の変更、intent 行です。

それを**確認したうえで**、新しいセッションの初期指示として渡します。制約を 2 つ付けました。

- **同じ provider の別プロファイルへは渡さない**。詰まった理由が契約側にあるとき、同じ CLI の別契約へ渡しても状況が変わらない場面がある
- **自動では起こさない**。文面を人が見てから押す

入口は 2 つあります。1 つはセッションの残量がしきい値を割ったときに出る隅の通知で、しきい値は `handoff.notify_remaining_percent` で変えられます（既定値は 10）。もう 1 つはサイドバーの「引き継ぎ一覧」ボタン（↪）です。設定キーの一覧はリポジトリの README にあります: https://github.com/ishizakahiroshi/many-ai-cli

後者はディスク上の看板を直接読むので、**Hub を再起動したあとでも、元のセッションが終わったあとでも開けます**。ここは意図的にメモリを経由していません。

引き継いだ側の看板には、どのセッションの続きかが記録されます。UI 上で 2 つのセッションが繋がって見えるのは、それだけです。

![詰まったセッションから、次のセッションへ紙を 1 枚渡す](https://raw.githubusercontent.com/ishizakahiroshi/qiita-content/main/public/images/08_2026-09-09_many-ai-cli-v080_illustration-handoff.png)

## ついでに、普通の新規セッションにも文面を渡せるようにした

引き継ぎのために「文面を持たせてセッションを起こす」経路を作ったので、それを普通の新規セッション作成にも出しました。

新規セッションのパネルに「初期指示（任意）」のテキストエリアがあります。そこへ書いたものが、`orchestrate spawn` の `--initial-prompt` と同じ経路で、立ち上がった CLI へ届きます。空なら今までどおりです。

引き継ぎ専用ではありません。plan ファイルのパスを 1 行書いて起こす、みたいな使い方が本命です。

## 初期プロンプトが入力欄に残ったまま送信されない問題

この経路で 1 つ大きなバグを踏みました。Claude の子セッションが、最初の指示を入力欄に入れたまま送信されず、60 秒後に起動失敗として殺される、という症状です。

原因は注入のタイミングでした。Hub は出力が 300 ミリ秒途切れたところで初期プロンプトを流し込んでいたのですが、Claude Code v2.1.263 ではその瞬間が **入力欄を描く前**でした。

テキスト自体は CLI が標準入力を読み始めたときに拾われます。ところが確定の Enter は、まだ入力欄が無い時点で送られているので落ちる。結果、文字だけが入力欄に残ります。

そのうえ、起動監視のウォッチドッグが 60 秒後に子を殺し、そのときのメッセージが「モデルか認証の設定を確認してください」でした。**観測していない原因を名指ししていた**わけです。

直したのは 4 点です。

1. Claude Code の入力欄フッター（`(shift+tab to cycle)`）が出るまで待ってから注入する
2. 入力欄からテキストが消えたことを確認して初めて「届いた」と扱う
3. 消えていなければ Enter をもう 1 回だけ送る
4. それでも駄目なら「まだ入力欄に残っています」と指揮者へ報告する

4 番目が地味に大事で、起動失敗の通知から推測を消しました。今は観測できたことだけを書きます。無操作の秒数、進捗ファイルが増えていないこと、画面の末尾。

# 第 3 層: 任せる範囲を広げる

## 指揮者 AI に「判断」をさせると壊れる

many-ai-cli には v0.4.0 から、1 つのセッションが指揮者になって子セッションを起こす仕組みがあります。

これを使って plan の章（C1, C2, …）を実装 → レビュー → 修正で回したい、とずっと思っていました。人間が毎回「次はレビューね」と言わなくても回るようにしたい。

最初に考えたのは、指揮者 AI にその進行を任せる案でした。やめました。

**AI に状態遷移を任せると、同じ状態を 2 回踏んだり、終わったはずの段へ戻ったりします。** 進行の記録が会話の中にしか無いからです。会話は圧縮されるし、要約されるし、途中で切れる。

なので relay ループは Hub 側の状態機械として実装しました。

```
internal/hub/relay.go          状態機械の本体
internal/hub/relay_worktree.go 専用 worktree の作成と回収
internal/hub/relay_store.go    relay.json への保存と復元
internal/hub/relay_api.go      HTTP API
internal/orchestrate/          many-ai-cli orchestrate relay
```

![relay の 1 ラウンド。判断は Hub、作業は子](https://raw.githubusercontent.com/ishizakahiroshi/qiita-content/main/public/images/09_2026-09-09_many-ai-cli-v080_qiita-fig5.png)

図のとおり、AI がやるのは実装とレビューと修正だけです。「次は何の段か」「あと何回回すか」「打ち切るか」は Hub が持ちます。

ラウンド数には明示的な上限があります。上限に達したら止まる。無限に回らない。オプションで「強い側のモデルへ上げて 1 回だけやり直す」エスカレーションも入れましたが、これも回数を持っています。

## 利用者のブランチには触らない

relay で一番怖いのは、勝手にコミットされることでも、勝手にマージされることでもありません。**作業中のブランチを動かされる**ことです。

なので設計の不変条件をもう 1 つ置きました。

- relay は自分専用の worktree の中だけで作業する
- 利用者のチェックアウトに触らない
- 自動マージはしない

`relay.json` に状態を保存しているので、Hub を再起動しても途中から再開できます。ここで問題になるのが「その worktree、本当にさっきの続きか」です。

v0.8.0 では、再利用する前に 3 つ照合するようにしました。親リポジトリの Git 共通ディレクトリ、登録されている worktree のパス、記録されているブランチです。

手でブランチを切り替えられていた、登録されていないディレクトリだった、別リポジトリの worktree だった。どれかに当たったら spawn や再開を止めます。**止めるだけで、利用者のチェックアウトとファイルには何もしません。**

## 同時に走らせると、上限をすり抜けた

子セッションの数には、親ごとの上限と全体の上限があります。

relay を複数同時に起動したとき、この上限をすり抜けられることが分かりました。それぞれが別々のスナップショットを見て「まだ枠がある」と判断していたためです。

予約を先に取ってから起動する形に変えました。予約の範囲は、通常の orchestration spawn、承認待ちの確認、relay の再開、タイムアウト後の再試行、強いモデルへのエスカレーションまでです。準備か起動に失敗したら予約は返します。

こういう「同時に来ると壊れる」系は、1 つ直すと似た経路が他にもあることが多いので、経路を数えてから直すようにしています。

## 指揮者を起こす条件を絞った

子が動き出すと、今度は指揮者がうるさくなります。

v0.7.0 までは、子の進捗が出るたびに指揮者へ届いていました。しかも兄弟の子セッションにも配られていました。指揮者は届いた文面に反応するので、進捗が出るたびに何か喋る。

v0.8.0 で、**起こすのは対応が要るときだけ**に絞りました。

通常の進捗はダッシュボードのバッジになるだけで、指揮者へは届きません。兄弟にも配りません。

指揮者を起こすのは 5 種類です。

- 完了
- 起動失敗
- タイムアウトと無操作の警告
- 遅れて返ってきた spawn の結果
- 新しく足した `## QUESTION <role> session=<id>` マーカー

最後のものは、子が指揮者へ質問を投げるための書式です。今までは子が質問で止まっても、指揮者からは「進捗が無いセッション」にしか見えませんでした。

配送は上書きしない有限長の FIFO にしました。指揮者が承認待ち・作業中・モーダルを開いている・Codex のサイドスレッドにいる、のいずれかなら待ちます。空いたら指揮者のメインの入力欄へ入れます。

キューがあふれたときは、**イベントを捨てずに看板へ残し、代わりに「看板を見て」という参照だけを届けます**。黙って落とすのが一番まずい。

## 承認する前に、その子に何を与えるのかを見せる

これはセキュリティ側の修正ですが、任せる層の話なのでここに置きます。

子セッションを起こすとき、確認ダイアログが出ます。そこに出ていたのは、ロール・provider・モデル・作業ディレクトリ・プロンプトの 5 つでした。

出ていなかったのが、**その子がどの権限で起動するか**です。

`orchestration.child_full_bypass` が既定のままだと、codex の子は `--sandbox danger-full-access --ask-for-approval never` で起動します。他の provider もそれぞれの全許可相当で起動します。承認を押す人は、それを知らずに押していました。

v0.8.0 では、provider ごとの実効設定をダイアログへ送るようにしました。ここで気をつけたのは、**表示用に設定を組み立て直さない**ことです。実際に spawn が使うのと同じコードを走らせてその結果を送っています。そうしないと、片方だけ直したときに表示と実物がずれます。

承認者が provider を切り替えたら、表示も切り替わります。

**権限そのものは何も変えていません。変えたのは、押す前に何を知らされるかです。** relay の子は設計上この確認を通らないので、こちらは影響を受けません。

あわせて、承認待ちの確認が溜まりすぎないように上限も入れました。親ごとと全体の既存の orchestration 上限をそのまま使い、超えた要求は確認を作らずに HTTP 429 を返します。同じロールの置き換えと、遅れて来た人間の判断は今までどおり通ります。

## 「あとで再実行してください」が二重起動を生んだ

もう 1 つ、指揮者 AI の挙動に効いたバグがあります。

子の起動確認をブラウザで放置していると、CLI 側のタイムアウトが先に来ます。そのとき `many-ai-cli orchestrate spawn` が出していたエラーが「再実行してください」でした。

指揮者はそれを読んで、素直に再実行します。ところがその間に人が承認していると、子はすでに起動していて、2 回目の要求は HTTP 409 で弾かれます。指揮者から見ると「失敗したのでもう一度」→「衝突した」の繰り返しになる。

直したのは 2 点です。クライアント側の既定の待ち時間を 3 分から 5 分へ延ばし（`MANY_AI_CLI_SPAWN_TIMEOUT` で変えられます）、タイムアウトのメッセージから「再実行してください」を消して、**承認されれば子は起動し、セッション ID は orchestration の通知で届く**と明記しました。

エラーメッセージは AI にとってはそのまま指示になります。人間向けの慣用句をそのまま出すと、こういう形で返ってきます。

## 7 つ目の CLI と、任意の CLI

任せる先も増やしました。

![組み込み 7 本と、config.yaml で足す任意の CLI](https://raw.githubusercontent.com/ishizakahiroshi/qiita-content/main/public/images/10_2026-09-09_many-ai-cli-v080_qiita-fig6.png)

1 つ目が **Command Code**（`command-code`）です。Claude Code / Codex CLI / GitHub Copilot CLI / Cursor Agent CLI / Grok Build CLI / opencode に続く 7 本目として、spawn フォームと provider ドロップダウンに出ます。承認モードの選択は、この CLI 自身のフラグへ対応づけました。

- plan → `--permission-mode plan`
- auto / acceptEdits → `--auto-accept`
- 全許可 → `--yolo`

`many-ai-cli doctor` はインストール状況とサインイン状況を報告します。スラッシュコマンドと承認パターンのリソースファイルも同梱しました。

ただし **承認検出はまだ検証できていません**。実機の承認プロンプトを PTY で採取して突き合わせる作業が残っています。README にもそう書きました。アクションバーが拾わないときはターミナル側で答えてください、と。

ここは「対応済み」と書きたくなるところですが、書いた瞬間に嘘になります。段階を分けて、Terminal と spawn は対応済み、承認統合は fixture 検証待ち、という表記にしました。

なお OS 側のエイリアスである `cmd` / `cmdc` は provider の id にもサブコマンドにも使っていません。Windows の `cmd.exe` と衝突するためです。

2 つ目が **`custom_providers`** です。`config.yaml` を手で書けば、組み込み以外の任意の CLI を spawn ドロップダウンへ足せます。

```yaml
custom_providers:
  - id: my-cli
    label: My CLI
    command: my-cli --agent
    approval_pattern_source: <設定ディレクトリ配下の絶対パス>/my-cli-approval-patterns.md
```

足した provider は、組み込みと同じように PTY で起動してアタッチし、承認検出の対象にもなります。承認検出は 2 段構えで、承認らしい言い回しと選択肢のラベル（Yes / No / Allow / Deny など）を拾う汎用ヒューリスティックが全部の custom セッションで自動的に走ります。そのうえで `approval_pattern_source` を指定すれば、その CLI 固有の言い回しを足せます。

`command` の分解は自前でやっていて、**シェルには一切渡しません**。規則は小さく固定しました。

- 空白とタブが引数の区切り。連続は 1 つに潰す
- `"..."` は 1 引数、または引数の一部を囲む。引用符自体は取り除く
- `\` は常にただの文字。エスケープではない（Windows のパスをそのまま書ける）
- 環境変数・`~`・glob・シェル演算子は展開しない。全部リテラルの引数テキストとして渡る
- 閉じていない引用符と空の command は、何かが始まる前に拒否する

組み込みのものは何も付きません。`--model` も、権限モードやサンドボックスのフラグも、ベンダー固有の環境変数プリセットも、Ollama のルーティングも、契約プロファイルの選択も付きません。どれも任意の CLI に対して意味が決まらないからです。spawn フォームはモデル欄を隠します。

そして **これは玄人向けの設定で、組み込みリストに掛けている審査は一切掛かっていません**。Gemini CLI を組み込みから外しているような利用規約の判断は、あくまで組み込みリストについての話です。`command` に何を指すかは完全に利用者の選択で、その CLI の規約を確認するのは利用者側の責任になります。`doctor` は設定されている custom provider の数を報告しますが、spawn のたびに警告は出しません。

## 委譲を 6 本中 5 本へ広げた

任せる話をもう 1 つ。

「普通に始めたセッションから、子セッションへ作業を委譲する」経路を広げました。今までは orchestration の指揮者からしか届きませんでした。

それと、**AI に「委譲できる」ことを教える文面の置き場所を変えました**。

今まではその案内を `approval-rules.md` に書いていました。このファイルは Hub と CLI のあいだの書式の約束（承認マーカー、完了サマリー、orchestration のエラー行）を載せるためのもので、機能の案内は責務が違います。しかも全セッションの常駐文脈を恒久的に消費します。

なので version 19 で足した節を version 20 で撤去して、provider ごとの届け方へ移しました。届け方は CLI ごとに違うので、6 本すべてに `--help` を実行して確認してから決めています。Claude なら `--append-system-prompt-file` にセッション所有の一時ファイルを渡す、という具合です。

そのうえで、再混入を止めるテストを `approval_rules.go` に置きました。常駐文脈は放っておくと必ず太るので、テストで蓋をしておくのが確実です。

# 3 層に入らなかったもの

ここからは、層で括れなかった変更です。数が多いので、効いたものだけ書きます。

## サイドバーを 1 本の木にした

orchestration の子セッションが、親と違うグループへ落ちていました。しかも別リポジトリの子まで同じ箱に同居する。

原因は 2 つありました。

1 つは、プロジェクトに ID が無く、cwd の末尾のフォルダ名から毎回推測していたことです。しかもその導出コードが 3 か所にコピーされていました。relay の worktree は `<親cwd>/<worktree_dir_root>/<id>/relay` で終わるので、**箱の名前が必ず「relay」になります**。別リポジトリの relay も全部そこへ入る。

もう 1 つは、配置を決める仕組みが 4 つ（`sessionOrder` / `groupOrder` / `projectFavorites` / `pinned`）あって、そのうち `pinned` だけが並び順ではなく**所属そのもの**を書き換えていたことです。

不変条件を 1 つ置いて解きました。

> サイドバーは 1 本の木を描く。木の形はデータだけが決める。ユーザー操作は木の形を変えず、同じ親を持つ兄弟の順序と、畳む／畳まないだけを変える。

Hub が `project_id` を配ります。worktree でも本体と同じ値になるよう、`rev-parse --path-format=absolute --git-common-dir` を使いました。`--show-toplevel` は worktree 自身を返すので使えません。

配置の計算は `web/src/app/sidebar-tree.ts` の純関数へ切り出して、フィクスチャでテストしています。

## 全画面 TUI のスクロールが 13 行飛んでいた

Claude Code や opencode のような全画面 TUI（代替画面バッファ）でのスクロールは、PageUp / PageDown を送っていました。端末 35 行での実測で、1 操作 13 行飛びます。32 行なら 12 行。

そのせいで、画面の上端や下端にまたがったコードブロックを画面内に収められず、**コピーしたい範囲を選択できませんでした**。

素直に「ホイールイベントを送ればいい」となるのですが、そこに罠がありました。

CLI 側はマウス追跡を有効にしています。実測したセッションの生ログには `ESC[?1000h` / `?1002h` / `?1003h` / `?1006h` がそれぞれ 90 回出ていて、対応する OFF は 0 回でした。ところが **xterm.js は選択を守るため、parse のたびに追跡をローカルで解除します**。なので `term.modes` を見ても「追跡が有効か」は分かりません。

PTY の出力を自前で走査して判定し、SGR のホイール（`ESC[<64;col;rowM`）を送るようにしました。SGR が無ければ X10、追跡が無効ならこれまでどおり PageUp / PageDown へ落ちます。

疑似スクロールレールの単位もページからノッチへ揃えました（仮想範囲 4 → 48、1 操作の上限 30 → 120）。上下ボタンは 1 クリック 12 ノッチです。

## 承認を台帳に記録した

承認マーカーは必ず出ているのに、**保留中の承認はライブ配信を受け取ったブラウザタブのメモリにしか無い**状態でした。そのタブが 1 度取りこぼすと、Hub にもディスクにも復元元が残りません。過去に何を承認したかを見る画面もありませんでした。

台帳自体は `sessionstore` に `approvals` テーブルとして既にありました。ただし書き手が VT ミラー経路だけ、読み手が件数カラムだけ、という半分の状態でした。

新しい保存先を作らず、この 1 本を書き手と読み手の両方へ繋ぎました。`provider` / `candidate_key` / `source_epoch` / `block` を足して、既存 DB 向けの `ALTER TABLE` 移行を入れています。マーカー経路からも記録し、抑止した壊れたブロックは書きません。選択肢は解かずにブロックの原文を持ちます。

## 端末が前のフレームを消したら、承認が抑止された

これは v0.7.0 から続いていた承認検出の残りです。

Hub の VT ミラーが `CSI n X`（erase characters、ECH）を実装していませんでした。Claude Code や Grok が短くなった承認ブロックを描き直して、余った行を ECH で消したとき、**古い終了マーカーの断片がミラーにだけ残ります**。

抽出側はその古いマーカーをブロックの終わりだと解釈し、構造チェックが `marker_leak` として弾き、利用者には承認バーの代わりに抑止のバナーが出ました。

2026-09-01 から 2026-09-07 のあいだに記録した 4 件のダンプを再生したら、3 件の `marker_leak` がすべて決定的に再現しました。ECH を実装したら 3 件とも通ります（`internal/hub/vt_buffer.go` の `eraseChars`）。

## 承認の質問が、勝手に消えていた

もう 1 つ承認まわりで大きいものを。

`[MANY-AI-CLI]` の質問が、ダッシュボードから消えて「↻ 承認」を押さないと戻らない、という症状がありました。

Hub は Claude と Codex について、この質問を CLI 自身のトランスクリプトから配っています。トランスクリプトは、端末が描いた内容より **1 分以上先を走ることがあります**。

ブラウザ側は「この質問はまだ画面に出ているか」を、選択肢のラベルと端末テキストの照合で判定していました。Ink の部分再描画でその照合が外れ、**未回答の質問を閉じてしまい、再配信もされない**。

トランスクリプト由来の質問については、閉じる判断をブラウザからやめて Hub に寄せました。Hub はトランスクリプトに次のメッセージ（端末へ直接打った回答を含む）が出た時点で質問を閉じ、開いている全ダッシュボードへ伝えます。セッションを切り替えたときと再接続したときは、承認台帳から保留中の質問を復元します。↻ ボタンが元々使っていた経路と同じです。

あわせて、ダッシュボードから答えたマーカー承認が台帳で解決済みにならない問題も直しました。照合にブラウザ側の署名を使っていて、それが永久に一致しなかったためです。

# セキュリティ側の修正

v0.8.0 の Security 節は 20 項目あります。監査で出た指摘への対応が中心です。全部は書けないので、設計として意味があったものだけ。

## 「全アクセス失効」が、開いているタブを切っていなかった

設定の「リモートアクセス保護」にある **全アクセス失効** は、端末を紛失したときのキルスイッチです。

これがトークンと PIN セッションをローテーションしていながら、**すでに繋がっている WebSocket をそのまま生かしていました**。

古いダッシュボードを開いたままのブラウザは、再接続するまで入力を送れて出力も受け取れます。失効を押したのに、押した本人からは何も変わったように見えない。これは効いていないのと同じです。

UI の登録・受信ループ・ブロードキャスト・キューされた入力の経路を、認証の世代（generation）に紐づけました。失効が成功すると世代が上がり、既存の UI 接続を全部閉じます。

ラッパー側の接続は触りません。走っている CLI を切らないためです。

## 承認が 2 回送られることがあった

同じプロンプトに対する ワンタップ承認・バッチ承認・自動承認 が同時に走ると、それぞれが自分の回答を CLI へ送れてしまう状態でした。送信と、消費・確定のステップが 1 つの予約の下に収まっていなかったためです。

予約の範囲を「送信から確定まで」に広げました。署名・候補・世代・ラッパーが同じであれば、2 つ目の回答は送られません。送信がきれいに失敗した場合の再試行は残しています。

**1 承認 1 キーストローク**は、このツールがずっと守ろうとしている性質です。承認が二重に飛ぶと、AI から見ると 2 回答えられたように見えます。

## 書き込みリダイレクトが「読み取り専用」に分類されていた

自動承認とバッチ承認の低リスク判定に穴がありました。

`cat x > file` と `git branch -D name` が、**読み取り専用のコマンド名で始まっている**という理由だけで低リスク側へ入っていました。前者はファイルを上書きし、後者はブランチを消します。

引用されていない出力リダイレクトと、ブランチの作成・削除・移動を中リスクへ上げました。引用済み・エスケープ済みの `>`、`2>/dev/null`、`2>&1` は読み取り専用のままです。

あわせて、`find` の副作用オプション（`-exec` / `-execdir` / `-ok` / `-okdir` / `-delete`）とコマンド置換（`$(...)` とバッククォート）も自動承認のハードブロックへ追加しました。広めの利用者ルールの後ろで低リスクのゲートを通れてしまう形でした。

## フォルダ限定の自動承認ルールが、フォルダに一致していなかった

ダッシュボードから追加できる「このフォルダのときだけ」の自動承認ルールで、作業ディレクトリを **生の正規表現として保存していました**。

結果、Windows では `C:\work\project` が一度も一致しません（`\` がエスケープとして解釈される）。一方で `/work/app` は `/work/application` にも一致してしまいます。

ダッシュボードからはアンカー付きでエスケープしたパターンを保存するようにしました。YAML に手で書いた `working_dir` の正規表現は今までどおりです。

## 削除 API が、別名で辿ったワークスペースのルートを消せた

ルートを守るガードが、解決済みのパスと字面のルートを比較していました。セッションの cwd が junction や symlink の別名で、渡されたのが実体のパスだと、**ルート自身を消せました**。

正規化したパスとファイルの同一性で比較するようにして、同一性が解決できないときは操作を拒否します。

## そのほかのセキュリティ修正

- ファイル保存の競合チェックが、基準の mtime を秒に丸めて比較していた。同じ秒の中で外部から編集されると黙って上書きされる。全精度で比較し、409 応答も全精度の現在 mtime を返すようにした
- 複数ファイルの移動が失敗したときのロールバックが、素の rename を使っていた。元の場所に別プロセスが作ったファイルがあると、それを消してしまう。前進側と同じ「置換しない rename」に変えた。衝突したら両方残し、移動したデータがどこにあるかを結果で示す
- 許可ルートの外にあるファイルの読み取り拒否リストが、`id_rsa` の接頭辞しか見ていなかった。`id_ed25519`（もう何年も `ssh-keygen` の既定）と `id_ecdsa` / `id_dsa` が素通りしていた。OpenSSH の既定の鍵名を全部見るようにして、`.netrc` / `_netrc` / `.npmrc` / `.pypirc` / `.git-credentials` / `.htpasswd` と SSH の authorization / known_hosts 系も拒否に足した。**設定と認証情報が同居する形式のファイル**が丸ごと抜けていた
- バグレポートの伏字処理が、このツール自身の秘密を 3 つ通していた。キーと値の照合が完成した名前（`api_key` / `auth_token` / `client_secret`）を列挙する形だったので、`auth_cookie_secret` / `remote_pin_hash` / `vapid_private_key` が一致しなかった。末尾の語で照合する形に変え、`key` と `hash` は秘密っぽい修飾語が前に付いたときだけ数えるようにした（`cache_key` と `commit_hash` は読めるまま）
- `hub.trusted_networks` に `/24`（IPv4）/ `/64`（IPv6）より広い CIDR を書けた。設定エラーとして起動時に止めるようにした。tailnet 全体のような広い private レンジは `hub.allowed_hosts` とトークンで扱う
- 通知音のアップロードが、判定した content type が `audio/*` でなくてもクライアントの `Content-Type` ヘッダを信じて通す経路を残していた。アバターのアップロードは content type を一切見ていなかった。どちらも中身を判定して、アバターは PNG / JPEG / GIF / WebP 以外を 415 で拒否する（SVG はスクリプト埋め込みのリスクがあるので拒否）
- アバターの配信 URL に Hub のトークンがクエリ文字列で載っていた。エンドポイント自体は元々トークン / cookie のガードを要求していたので権限は変わらないが、ブラウザの履歴・リファラ・ログへトークンが漏れる経路だった。`/api/avatar` から外した
- `findGitRoot` が、たまたま git リポジトリになっているホームディレクトリを git ルートとして採用していた。Files API のスコープと relay の worktree の基点がホーム全体へ広がる
- リリースワークフローが、公開用の認証情報と同じプロセスでサードパーティのコードを走らせていた。GoReleaser のステップは Homebrew tap と winget fork へ push できるトークンを持つのに、その `before` フックで web の依存インストールとツールのインストールを走らせていた。フックを認証情報の無い前のステップへ移し、GoReleaser は `--skip=before` で呼ぶようにした
- Docker のビルドコンテキストから、認証情報・ローカルの AI 状態・worktree・ログ・トランスクリプトを除外した。ベースイメージ・Whisper のソース commit・provider CLI のバージョン・Cursor のアーカイブを固定して、使う前に検証する。provider CLI は追跡している npm の lockfile からインストールする

## Docker イメージに同梱していた CLI に脆弱性が出た

タグを打った後の push で、GitHub が Dependabot の警告を返してきました。

Docker イメージは provider CLI を同梱しています。そこに固定していた Claude Code のバージョンに、サンドボックス脱出とデータ持ち出しの 2 件が出ていました。

影響するのは Docker イメージ経由で使う場合だけで、バイナリ・npm・Homebrew・winget で入れた人は自分の Claude Code を使うので対象外です。それでも同梱している以上こちらの責任なので、上げました。

ここで引っかかったのが、**バージョンのピンが 4 か所ある**ことです。

```
deploy/docker/provider-cli/package.json      dependencies
deploy/docker/provider-cli/package-lock.json ルートと各エントリ
deploy/docker/Dockerfile                     ARG PROVIDER_CLAUDE_CODE_VERSION
scripts/check-docker-build-inputs.mjs        期待値のテーブル
```

4 つ目があるおかげで、3 つ目までのどれかを直し忘れると検査が落ちます。lockfile は `npm install --package-lock-only` で作り直すと、対象パッケージとそのプラットフォーム別 8 パッケージの 9 エントリだけが変わり、他の provider と推移的依存は動きません。

## ローカルでだけ落ちるテストの正体は改行コードだった

Docker のビルド入力を検査するテストが、Windows のローカルでだけ 1 件落ちていました。CI（Linux）では通ります。

原因は改行でした。`.gitattributes` が `* text=auto` なので、Windows の checkout でそのファイルが CRLF になります。テストは LF 前提で `replace('\n.npmrc\n', '\n')` という文字列置換をして「1 行抜いた入力」を作り、エラーが出ることを確かめる作りでした。

CRLF だと置換が空振りします。入力が無傷のままなのでエラーが出ず、アサーションだけが落ちる。

`.gitattributes` にそのファイルの `eol=lf` を 1 行足して、作業ツリーのコピーを入れ直したら 10 件すべて通るようになりました。git 側の blob は元々 LF なので、内容は変わりません。変わるのは Windows での checkout 結果だけです。

**ローカルだけ落ちるテストを見たら、まず行末を疑う。** 環境のせいにして流すと、次に同じファイルを触った人がまた同じ 10 分を使います。

最後は自分の作業のほうの話です。

| D-01 | Gemini CLI を wrap 対象に入れる（利用規約上の制約） |
| D-02 | 新規 provider を増やす（20 製品を調査して全件見送り） |
| D-05 | Copilot / Cursor Agent の複数サブスクリプション対応 |
| D-06 | OpenRouter を接続先として載せる |
| D-11 | 認証済み Hub token をユーザー等価より狭める |
| D-12 | orchestration の子の全許可バイパスを既定 off にする |

D-05 は、この記事の第 1 層で「未対応」と書いたものです。技術的に無理だと分かったので、対応予定ではなく見送りとして台帳に置きました。

D-12 は v0.8.0 の直前に足した行です。承認ダイアログに実効権限を出す作業をしていて、「ついでに既定を安全側へ倒すべきでは」と考えました。やめました。既定を off にすると relay が無人で回らなくなり、spawn の確認は既に必須なので、守りは 1 枚足りているという判断です。

台帳に共通して書いてある却下理由も 1 つあります。**候補の人気・伸び・他社の対応状況・利用者増の見込みを根拠にしない**。このツールの規模（star 6 / npm 週次 11・2026-08-14 実測）では、それらを根拠に採否を決める枠組みが成立しません。起点は「作者が実際に使っていて、日常の並列運用に入っているか」です。

# 実際どう回しているか

コマンドだけ置いておきます。

```bash
# Hub を立てる（Windows はトレイのショートカットでも可）
many-ai-cli serve

# provider をサブコマンドで起動する。Hub が落ちていれば自動で立つ
many-ai-cli claude
many-ai-cli codex
many-ai-cli command-code

# 指揮者セッションから子を起こす
many-ai-cli orchestrate spawn --role impl "docs/local/plan_xxx.md の C1 を実装して"

# 生きている子へ追加指示を送る（同じロールで spawn し直すと 409 になる）
many-ai-cli orchestrate send --role impl "レビュー指摘 3 件を直して"

# plan を実装 → レビュー → 修正で回す
many-ai-cli orchestrate relay --plan docs/local/plan_xxx.md

# 状態確認と停止
many-ai-cli status
many-ai-cli stop
```

`orchestrate relay` は専用の worktree を作って、そこで回します。利用者のチェックアウトには触りません。途中で Hub を落としても `relay.json` から再開できます。

自分の使い方だと、契約を 2 本積んでいるのは Claude だけです。片方を対話用、もう片方を relay 用にしています。relay は無人で長く回るので、対話中のセッションと枠を食い合わせたくないからです。

# 設計ルールを、文章のまま持たない

この記事でここまで「設計の不変条件」という言い方を何度かしました。最後にその運用の話を書きます。v0.8.0 で足した仕組みが 4 つあるので。

## AI 向けの指示ファイルが 5 週間で倍になった

このリポジトリには `CLAUDE.md` があります。AI CLI が全セッションで全文を読むファイルです。

これが 5 週間で 129 行から 269 行へ倍増しました。増えた 93 行は 7 つの節で、どれも「〜した事故があったので、今後は〜する」という形の制定でした。

問題は、**増えた 7 節すべてに、別の場所に正本があった**ことです。設計書、台帳、検査スクリプト、コード本体。そちらに書いてあることを、指示ファイルへ改めて書き写していました。

そして指示ファイルは全セッションで全文が読まれます。**いちばん高くつく置き場所へ、いちばん安易に積んでいた**わけです。

## 索引に戻して、機械検査で止める

v0.8.0 に向けた作業で `CLAUDE.md` を索引へ再編しました。各行は「ルール 1 行」「正本のパス」「機械検査の名前」の 3 列だけを持ちます。

```
| ルール | 正本（本文はここ） | 機械検査 |
|---|---|---|
| 承認の同一性は 1 本だけ | internal/hub/approval_identity.go | TestApprovalSuppressionStateIsSingleSource |
| auto 選択は round-robin だけ | internal/hub/subscription.go | TestAutoSubscriptionNeverConsultsUsage |
| サイドバーは 1 本の木 | web/src/app/sidebar-tree.ts | sidebar-tree-fixtures.ts |
| 引き継ぎ看板は型で受ける | internal/handoff/handoff.go | handoff_test.go の allowlist 固定 |
| 残量ソースは 1 本の表 | internal/subscription/usage_source.go | usage_source_test.go |
```

下の 3 行が v0.8.0 で足したものです。この記事の第 1 層と第 2 層で書いた不変条件が、そのまま行になっています。

再肥大は `scripts/check-claude-md.mjs` が CI で止めます。見るのは 3 つです。全体の行数予算、1 節あたりの行数上限、そして**「制定」型の節が正本を名指ししているか**。

名指しできない節は、そこにしか無いルールです。そういうものは破られても誰も気づけないので、検査かコードのコメントへ移します。

## 新しいルールを足したくなったら、まず検査にできないかを見る

運用として、置き場所は読まれるコストの安い順に当てはめます。

1. 機械検査（誰も読まない。破ると落ちる）
2. 触るファイルの先頭コメント（そのファイルを開いた人だけが読む）
3. skill（起動語で呼ばれたときだけ読まれる）
4. guide（トリガー時に読まれる）
5. 台帳（提案や着手の前に読む。増えても 1 行）
6. 指示ファイル（全セッションで全文）

**1 が使えるのに 6 へ書くのが、いちばん多い失敗です。** 「検査を書くのが面倒」は理由になりません。文章は破られても誰も気づきませんが、検査は破れない。

1 と 2 は併用します。検査だけだと「なぜ駄目か」が伝わらず、コメントだけだと守られないからです。

そして、**検査を書いたら同じコミットで指示ファイル側の節を 1 行に縮めます**。昇格の仕組みだけあって降格の仕組みが無いと、一方向のラチェットになって必ず太ります。

## 観測コードをリリースに混ぜない

似た発想で、調査用に仕込んだ計測コードの扱いも仕組みにしています。

台帳（`instrumentation.json`）に登録し、ビルドタグでオプトインにして、成果物を検査する。ランタイムのフラグで既定 off にしているだけの状態は「入っていない」と扱いません。既定 on のまま出荷する、ゲート自体を書き忘れる、ゲートの外で入力バイトを保存する。全部実際に起きる失敗の形です。

v0.8.0 のリリースワークフローでも、ビルドした `dist` を `scripts/check-artifact-clean.mjs` に通しています。ソースを見て「消したはず」で済ませない、という線引きです。

## many-ai-cli はこんなときに刺さります

- Claude Code、Codex、Copilot、Cursor、Grok、opencode、Command Code を同時に走らせていて、どれが止まったか分からなくなる人
- 承認待ちを捌くためにターミナルを行き来していて、その往復を減らしたい人
- 離席中もスマホから承認だけ返しておきたい人
- **同じ CLI の契約を 2 本持っていて、片方が上限に当たるたびに手で切り替えている人**
- **長いセッションが詰まったとき、そこまでの経緯を新しいセッションへ書き写している人**
- **plan の章を実装 → レビュー → 修正で回すのを、毎回自分で指示している人**

いずれかに心当たりがあれば、`npm i -g many-ai-cli` と `many-ai-cli setup` の 2 コマンドで試せます。設定ファイルを書く必要はありません（`custom_providers` を使うときだけ `config.yaml` を手で書きます）。

## おわりに

78 項目を 3 つの層に並べ直してみて、自分でも意外だったのは、**どれも「AI に何かをさせる機能」ではなかった**ことです。

契約を積む層がやっているのは、環境変数を差し替えることだけ。引き継ぐ層は、型で決めた 10 行程度のレコードを jsonl へ追記しているだけ。任せる層に至っては、AI から判断を取り上げて Hub の状態機械へ移す話でした。

AI が賢くなるほど、周りに要るのは**賢くない部分**なんだと思います。誰がどの契約で動いているか。何をどこまでやったか。次は誰の番か。この 3 つは、AI に覚えさせるより外に置いたほうが確実でした。

とはいえ Command Code の承認検出はまだ検証できていませんし、Claude と Grok のスラッシュコマンド一覧は 3 リリース続けて実機の採取を後回しにしています。全部埋まってはいません。

小さく。次に触るときは、前回の調査結果を先に開くところから始めます。
