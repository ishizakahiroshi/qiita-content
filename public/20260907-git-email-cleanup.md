## 「ソースには書いていないから大丈夫」が一番あぶない

Git の commit には、author と committer という 2 つの署名が入ります。名前とメールアドレスと日時です。ファイルの中身とは別のところに、静かに、全部載っています。

commit オブジェクトの中身を直接見ると分かりやすいです。

```bash
git cat-file -p HEAD
```

```text
tree 4b825dc642cb6eb9a060e54bf8d69288fbee4904
parent 0123456789abcdef0123456789abcdef01234567
author  名前 <メールアドレス> 1757203800 +0900
committer 名前 <メールアドレス> 1757203800 +0900

コミットメッセージ
```

author はそのコードを書いた人、committer は実際にコミットを作った人です。自分で書いて自分でコミットすれば同じ値になりますが、cherry-pick や rebase をすると committer だけ変わります。GitHub の Squash and merge を使うと committer が GitHub 側のアドレスになります。

そして、この行がそのままリポジトリの中に残ります。`.patch` を開けば誰でも読めます。GitHub なら commit の URL の末尾に `.patch` を付けるだけです。

```text
https://github.com/<owner>/<repo>/commit/<sha>.patch
```

認証も要りません。公開リポジトリなら、ブラウザでもコマンドでもそのまま読めます。「メールアドレスをソースに書かない」という意識は持っていても、この層は視界に入っていませんでした。

自分の場合、私用の Gmail のままになっている commit が 329 件ありました。書き換え前のバックアップから数え直した実測です。

期間を見て、これはちょっと効きました。

- 最古: 2026-04-25
- 最新: 2026-09-05

月別だと 4 月が 1 件、5 月が 119 件、6 月が 163 件、7 月が 35 件、8 月が 9 件、9 月が 2 件です。

そして開発用アドレスの初出は 2026-06-21 でした。つまり **6 月下旬には切り替えているのに、そのあとも 7 月に 35 件、8 月に 9 件、9 月に 2 件と混ざり続けていた**ことになります。最後の 1 件は、この掃除をする 2 日前です。

「昔の分が残っている」ではありませんでした。**切り替えたつもりで、切り替わっていなかった**話です。

原因は追い切れていません。マシンやクローンごとに `user.email` が別々に効くので、どこかで global 設定が使われていない経路が残っていたのだと思いますが、そこは推測です。実測できたのは日付の分布までです。

その日のうちに片付けることにしました。着信から回答の返信までで 2 時間 57 分。記事の題名にするなら「約 3 時間」です。その 3 時間の内訳は、問い合わせへの回答と、この履歴整理の 2 本立てでした。

以下は履歴整理のほうの記録です。同じことをやる人が踏みそうな穴を、遭遇した順に全部書きます。

先に結論だけ言うと、**branch と tag からは消えました。`refs/pull` からは消えていません。** 消えていないものを「消えた」と書かないのが、この手の記事でいちばん大事なところだと思っています。

## まず数える。「たぶん入っていない」を潰す

作業に入る前に、どこに何件あるのかを確定させました。

ここを飛ばすと、後で「あれも直さないと」が出てきて、force push を 2 回打つことになります。commit の SHA が全部変わる操作を 2 回やるのは、それだけで事故の種です。

数えたのは 5 か所です。

### 1. commit の author と committer

これが本命です。全 ref を対象にします。

```bash
git log --all --pretty=format:"%ae%x09%ce"
```

`--all` を付けないと、今チェックアウトしているブランチしか見ません。develop にしか居ない古い commit を丸ごと見落とします。

出力を旧アドレスで絞って数えるだけです。私は Windows なので PowerShell で回しました。

```powershell
$hits = @(git log --all --pretty=format:"%ae`t%ce" | Where-Object { $_ -like "*$old*" }).Count
```

### 2. ファイルの中身（過去の commit を含む）

「今の HEAD に無い」ことと「履歴のどこにも無い」ことは別です。`git grep` は基本的に今の内容しか見ません。過去も含めて探すなら `-S` を使います。

```bash
git log --all --pretty=format:"%h" -S"探す文字列"
```

`-S` は、その文字列の出現回数が変化した commit を拾います。つまり「いつ入って、いつ消えたか」が出ます。0 件なら、一度も入ったことがないということです。

似たオプションに `-G` があります。こちらは差分そのものを正規表現で引きます。行が移動しただけの変更まで拾うので件数は増えますが、「入ったか出たか」を知りたいときは `-S` のほうが素直です。今回は「一度でも入ったことがあるか」を知りたいので `-S` を使いました。

もっと確実にやるなら、全 blob を舐める手もあります。

```bash
git rev-list --objects --all | \
  git cat-file --batch-check='%(objecttype) %(objectname) %(rest)' | \
  awk '$1=="blob" {print $2, $3}'
```

これで全リビジョンの全ファイル実体が列挙できるので、あとは中身を引くだけです。ただ、リポジトリが大きいと時間がかかります。今回は `-S` が全部 0 件だったので、そこまではやりませんでした。

`-S` は追跡されているテキストファイルの差分しか見ないので、バイナリの中に埋まっている文字列は拾えません。そこが気になるなら上の全 blob 走査が要ります。自分の場合、公開しているのはソースとドキュメントとリリース用のスクリプトなので、そこは割り切りました。

自分の 23 本は、ここが全部 0 件でした。

### 3. GitHub の code search

ローカルの clone が最新でない可能性があるので、GitHub 側からも引きます。

```bash
gh api -X GET search/code -f q="探す文字列 user:<自分のユーザー名>"
```

0 件でした。

### 4. gist

意外と忘れます。gist は別の場所にありますが、公開されているものは公開されています。

```bash
gh api gists --jq '.[] | "\(.public) \(.id) \(.description)"'
```

そもそも 1 件も作っていませんでした。

### 5. 注釈付きタグの tagger

ここが今回いちばんの落とし穴でした。

`git tag -a` で作った注釈付きタグは、commit とは別に tagger という署名を持ちます。名前とメールと日時です。commit を全部書き換えても、タグの中に古いアドレスが残ります。

```bash
git for-each-ref --format="%(taggeremail)" refs/tags
```

3 本のリポジトリで、4 件、2 件、1 件が引っかかりました。commit だけ見ていたら、確実に取りこぼしています。

### 数え終わって分かったこと

旧アドレスが入っていたのは、**commit の author と committer、それと注釈付きタグの tagger だけ**でした。

README にも、ソースにも、設定ファイルにも、ドキュメントにも、package の metadata にも、過去 commit のファイル内容にも、1 件もありません。

## どこまでやるかを、手を動かす前に決めた

履歴の書き換えは戻せません。なので、着手前に方針を文章にしました。

決めたのは 4 つです。

**目的**: 今後 GitHub 本体から通常たどれる履歴・ソース・メタデータの上に、旧アドレスを残し続けないこと。

**割り切る範囲**: すでに第三者が clone した コピー、fork 済みのリポジトリ、検索エンジンのキャッシュ、Web Archive、外部サービスに保存された過去データ、誰かが取得済みの `.patch`。これらの完全削除は目的にしません。

**許容すること**: commit の SHA が全部変わること。古い SHA との互換性は捨てます。

**やらないこと**: メールアドレス整理以外の変更。ついでのリファクタリングをしない。履歴整理と新機能開発を同じ変更に混ぜない。

この 4 つを先に書いておくと、作業中に迷いません。「fork にも残ってるじゃん」と気づいたときに、方針を読み返して「それは割り切ると決めた」で済みます。

決めていないと、そこから 1 時間溶けます。

## 手順そのものは短い

やることは 5 段です。

1. 各リポジトリを mirror clone してバックアップを取る
2. `git filter-repo --mailmap` で置換する
3. GitHub Actions をリポジトリ単位で止めてから force push し、直後に元へ戻す
4. ローカルの作業クローンを新しい履歴へ張り替える
5. fresh clone して検証する

置換に使った mailmap は 1 行です。

```text
ishizakahiroshi <現在の開発用アドレス> <旧アドレス>
```

`.mailmap` の書式は 4 通りあります。

```text
新しい名前 <新しいメール>
<新しいメール> <古いメール>
新しい名前 <新しいメール> <古いメール>
新しい名前 <新しいメール> 古い名前 <古いメール>
```

上から順に、メールで引いて名前だけ直す、メールで引いてメールだけ直す、メールで引いて両方直す、名前とメールの組で引いて両方直す、です。左側が置換先で、右側が置換元。

今回は 3 番目を使いました。旧アドレスに一致する commit を、名前ごと現在の名義へ揃えています。

書式の正典は `gitmailmap` の man ページです。
https://git-scm.com/docs/gitmailmap

自分の場合、旧アドレスに紐づく表示名は 1 種類しかありませんでした。事前に確認しています。

```bash
git log --all --pretty=format:"%an <%ae>%n%cn <%ce>" | sort -u
```

表示名が複数あると、mailmap の行も増えます。「同じ人なのに Yamada Taro と yamada と taro-y の 3 通りある」というのはよくある話で、そこを見ずに 1 行だけ書くと取りこぼします。

### `--mailmap` は tagger まで面倒を見てくれる

これは知っておくと 1 工程減ります。`git filter-repo` の help にこう書いてあります。

> Use specified mailmap file (see git-shortlog(1) for details on the format) when rewriting author, committer, and tagger names and emails.

author と committer と tagger。3 つ同時です。タグのために別の処理を書く必要はありません。

git-filter-repo 本体はこちらです。
https://github.com/newren/git-filter-repo

実際、tagger に旧アドレスを持っていた 3 本も、`--mailmap` 一発で 0 件になりました。

### mirror clone をバックアップにする

バックアップは mirror clone で取りました。

```bash
git clone --mirror https://github.com/<owner>/<repo>.git <repo>.git
```

`--mirror` は refs を全部持ってきます。branch も tag も、GitHub が持っている `refs/pull/*` も含みます。これを触らずに残しておけば、いつでも元の状態に戻せます。

作業用には、このバックアップをコピーしたものを使いました。GitHub から 2 回 clone せず、ローカルでコピーするほうが速いですし、「バックアップと作業対象が同一の入力である」ことが保証されます。

普段使っている作業クローンをそのまま書き換えなかったのには、理由が 2 つあります。

1 つは、`git filter-repo` が「新しく clone した直後のリポジトリ」で動くことを前提にしている点です。既存の作業ディレクトリで動かすには `--force` が要りますし、書き換えのあとにリポジトリの状態を作り直すので、作業ツリーに置いてある未コミットの変更が巻き込まれます。手元には未コミットのファイルが残っているリポジトリがいくつもありました。ここを踏むと、掃除をしに行って自分の作業を消すことになります。

もう 1 つは、正本をはっきりさせたかったからです。書き換えの入力にすべきは「GitHub にある現在の状態」であって、「手元でどこまで pull しているか分からないクローン」ではありません。実際、あとで手元の 1 本が remote と完全に別系統になっていたことが分かるので、この判断は結果的に効きました。

### Actions を止める処理で気をつけたこと

小さい話ですが、2 つあります。

1 つ目は、**元の設定を読んでから戻す**ことです。`allowed_actions` は `all` とは限りません。ローカルアクションだけ、あるいは選択したアクションだけ、という設定にしているリポジトリもあります。戻すときに決め打ちで `all` を書くと、絞っていた設定が緩みます。しかも、緩んだことに気づく機会がありません。

2 つ目は、**戻す処理を必ず通る場所に置く**ことです。push が失敗する可能性は普通にあります（実際、最初の 1 本目は拒否されました）。そこで処理が止まって、Actions が無効のまま放置されると、次にタグを打ったときにリリースが走りません。しかも「なぜ走らないのか」がしばらく分かりません。

自分は push の呼び出しを try で囲って、finally に相当する場所で復元しています。復元したあとに `.enabled` を読み直して `true` を確認するところまでを 1 セットにしました。

**一時的に何かを止めるコードを書いたら、止めっぱなしになる経路を先に塞ぐ。** 当たり前ですが、23 本を順に回すループの中だと、1 本目で例外が出た時点で残り 22 本の設定がどうなっているか分からなくなります。

### リポジトリを作り直す案を捨てた理由

`refs/pull` を確実に消す方法は、実はもう 1 つあります。リポジトリを削除して、同じ名前で作り直して、書き換え後の履歴を push することです。PR は存在しなくなるので、`refs/pull` も消えます。

やりませんでした。理由は 3 つです。

- star が消える。数は多くありませんが、付けてくれた人の操作を勝手に無かったことにするのは違うと思いました
- issue と PR の議論が消える。自分の記録でもあり、読んだ人が参照している可能性もあります
- Release とその資産が消える。バイナリを配っているものは、既存のダウンロード URL が全部 404 になります

消したいのはメールアドレス 1 つで、失うものが多すぎます。天秤にかけたら比べるまでもありませんでした。

Support への依頼が通らなかったとしても、この選択は変えないと思います。**掃除のために本体を捨てるのは、掃除ではありません。**

### push は refs を明示する

mirror をそのまま `git push --mirror` すると `refs/pull/*` まで押そうとして失敗します。あれは読み取り専用なので、押せません。

なので明示します。

```bash
git push --force --prune https://github.com/<owner>/<repo>.git \
  "refs/heads/*:refs/heads/*" "refs/tags/*:refs/tags/*"
```

branch と tag だけ。`--prune` は、手元に無くなった ref を向こうからも消します。

## ここから先が本題です。詰まったところ全部

手順自体は上の 5 段で終わりです。実際に時間を食ったのは、その周辺でした。遭遇した順に書きます。

### 全 ref の force push は、Actions を叩き起こす

これは push を打つ前に気づけて助かりました。

タグを同じ名前で force push すると、GitHub は tag push イベントを飛ばします。`on: push: tags:` で走るリリース用の workflow があれば、当然それが起動します。

23 本のうち、タグ駆動のリリース workflow を持っているものが 8 本ありました。npm への publish、PyPI への publish、GitHub Release の作成、Docker イメージのビルド。それが全部、過去のタグの本数ぶん一斉に走ります。

想像すると、なかなかの絵面です。すでに公開済みのバージョンを再 publish しようとして失敗する job が何十個も並び、Release の資産が上書きされるかもしれない。

なので、push の前にリポジトリ単位で Actions を止めました。

```bash
# 現在の設定を控える
gh api "repos/$owner/$repo/actions/permissions" --jq '.enabled'
gh api "repos/$owner/$repo/actions/permissions" --jq '.allowed_actions'

# 止める
gh api -X PUT "repos/$owner/$repo/actions/permissions" -F enabled=false

# push する

# 元に戻す
gh api -X PUT "repos/$owner/$repo/actions/permissions" -F enabled=true -f allowed_actions=all
```

`allowed_actions` は元の値をそのまま戻します。ここを決め打ちで `all` にすると、絞っていたリポジトリの設定を壊します。

戻す処理は `finally` に相当する場所に置きました。push が失敗しても Actions は必ず戻る形にしています。**途中で落ちて Actions が止まったまま放置される**のが、この手の細工でいちばん怖いパターンなので。

結果として、当日トリガーされた workflow run は 0 件でした。これは後で `gh api repos/.../actions/runs` を叩いて確認しています。

### archive 済みのリポジトリは push できない

23 本のうち 2 本が archive 済みでした。read-only なので、当然 push は 403 で弾かれます。

```text
remote: This repository was archived so it is read-only.
fatal: unable to access '...': The requested URL returned error: 403
```

archive したまま履歴を書き換える方法はありません。一時的に解除するしかない。

```bash
gh api -X PATCH "repos/$owner/$repo" -F archived=false
# push する
gh api -X PATCH "repos/$owner/$repo" -F archived=true
```

解除して、押して、すぐ戻す。ここも戻し忘れると、archive したはずのリポジトリが開いたままになります。実行後に `.archived` を読み直して `true` を確認しました。

archive は「もう触らないと決めた」という宣言なので、勝手に開いたままだと自分の意図と食い違います。

### プライバシー設定が有効だと、force push が全滅する

ここでいちばん時間を使いました。

1 本目の push が、こう言って拒否されました。

```text
remote: error: GH007: Your push would publish a private email address.
remote: You can make your email public or disable this protection by visiting:
remote: https://github.com/settings/emails
```

GitHub の設定に「Block command line pushes that expose my email」というチェックがあります。これが入っていると、push しようとしている commit の author メールがアカウントの非公開アドレスと一致した場合に、push を止めてくれます。

公式の説明はこちらです。
https://docs.github.com/en/account-and-profile/setting-up-and-managing-your-personal-account-on-github/managing-email-preferences/blocking-command-line-pushes-that-expose-your-personal-email-address

親切な機能です。ただ、今回の作業とは相性が最悪でした。

理由は単純で、**force push では過去の commit も全部「新しい commit」として検査対象になる**からです。書き換えによって SHA が全部変わっているので、GitHub から見ると 20 件の新規 commit が来たことになります。そのうち 1 件でも非公開アドレスを持っていれば、push 全体が拒否されます。

普段の push は新しく作った 1 件か 2 件しか検査されないので、この設定が入っていても通ります。だから気づきません。履歴を全部押し直すときだけ、突然全滅します。

実際、拒否されたときの表示はこうでした。

```text
 ! [remote rejected] main -> main (push declined due to email privacy restrictions)
 ! [remote rejected] v0.2.0 -> v0.2.0 (push declined due to email privacy restrictions)
```

branch も tag も両方落ちています。ref 単位ではなく、push 全体が止まる挙動です。

ここで選択肢が 2 つに割れました。

**A. 置換先を GitHub の noreply アドレスにする。** `<数字ID>+<ユーザー名>@users.noreply.github.com` の形式です。これなら保護を有効にしたまま押せますし、以後も個人アドレスが公開履歴に入りません。

**B. 保護を一時的に外して push し、現在の開発用アドレスのまま進める。**

自分は B を選びました。開発用のアドレスは公開しているアドレスで、隠す前提のものではないからです。公開しているものを非公開扱いされて push が止まっているだけ、という状態でした。

もし「commit の名義も含めて個人アドレスを一切出したくない」なら A が正解です。その場合は `git config --global user.email` も noreply に切り替えないと、次の push でまた止まります。

**この設定は、有効化と個人アドレス名義が両立しません。** どちらを取るかを先に決めてから作業に入るべきでした。1 本目の push で初めて気づいたのは、単に事前調査が足りていません。

### 対象をローカルの clone ディレクトリから数えると漏れる

これは実際に漏らしました。

作業を 2 つのセッションで並行して進めていて（この話は後述します）、一方は「ローカルの作業フォルダに clone してあるリポジトリ」を列挙していました。18 本です。もう一方はアカウントから引いて 23 本でした。

差分の 5 本は、ローカルに clone していないリポジトリでした。記事の原稿を置いてあるもの、配布用の設定を置いてあるもの、実験して放置してあるもの。手元に無いだけで、GitHub 上では普通に公開されています。

さらに fork したリポジトリが 1 本、どちらの列挙にも入っていませんでした。

```bash
gh repo list <ユーザー名> --limit 200 --json name,visibility,isFork
```

これで引くのが正解です。**「自分が持っているリポジトリ」の正本は GitHub のアカウントであって、ローカルのフォルダではありません。** ローカルは、たまたま手元に降りてきているものの部分集合でしかない。

当たり前のことなのに、作業を始めるときは目の前のフォルダを `ls` してしまいます。

### `refs/pull` だけは、git からどうやっても消せない

push が全部通って、検証に入って、ここで気づきました。

fresh clone して数え直したら、3 本のリポジトリだけ 0 件になっていません。152 件、4 件、2 件。書き換え前とほぼ同じ数字です。

どこに残っているのか、ref 単位で見ました。

```bash
for r in $(git for-each-ref --format="%(refname)"); do
  n=$(git log --pretty=format:"%ae%x09%ce" "$r" | grep -c "探す文字列")
  [ "$n" -gt 0 ] && echo "$r : $n"
done
```

出てきたのは全部 `refs/pull/N/head` でした。branch でも tag でもありません。

`refs/pull/*/head` は、GitHub が pull request ごとに自動で作る ref です。PR を出した瞬間のブランチ先端を指しています。読み取り専用で、こちらから書き換えることも削除することもできません。`git push` の対象にすらなりません。

つまり、**PR を 1 回でも出したことがあるリポジトリでは、その時点の履歴が GitHub の中に凍結されている**わけです。branch を force push して古い commit を到達不能にしても、`refs/pull` からはたどれます。

PR のページを開けば commit の一覧が出ますし、その commit の `.patch` を開けば author のメールが読めます。到達不能な commit は GitHub の gc が回るまで SHA 直リンクでも生きています。

自分の場合、該当したのは closed / merged 済みの PR が 6 本、2 本、1 本の 3 リポジトリでした。数が少ないのは、個人開発なので PR をあまり使っていないからです。それでも 0 にはなりません。

消す手段は 2 つしかありません。

- リポジトリを削除して作り直す（star も issue も PR も release も失う）
- GitHub Support に依頼する

前者は論外でした。star を付けてもらっているリポジトリを、メールアドレスのために消す気にはなれません。

### 消せないものは、頼むしかない

GitHub の公式ドキュメントに、ちゃんと導線が書いてあります。

> you can permanently remove cached views and references to the sensitive data in pull requests on GitHub by contacting us through the GitHub Support portal.

出典はこちらです。
https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository

つまり、履歴を書き換えて force push するところまでは自分でやって、そのあとに残る「PR の中の参照」と「キャッシュされたビュー」は Support 側で消してもらう、という 2 段構えが正規の手順です。

依頼文には、次のものを入れました。

- いつ、どのツールで履歴を書き換えて force push したか
- branch と tag はすでにクリーンであること
- 残っているのが `refs/pull/*/head` と到達不能な commit であること
- 対象のリポジトリ URL と、それぞれの ref
- 消したい文字列そのもの
- 対象の PR が全部 closed か merged であること
- 自分が単独の所有者で、他に collaborator が居ないこと
- PR ページの commit や diff が消えることを了承していること
- `git filter-repo` が出力する first changed commit の値

最後のものは、依頼を出す途中で GitHub 側から求められました。`filter-repo` は書き換えのあとに、作業リポジトリの中へ「最初に変わった commit」を記録したファイルを残します。旧 SHA と新 SHA が 1 行で並んでいるやつです。これがあると、Support 側で「どこから先が書き換わったのか」を機械的に特定できます。

自分は作業用のリポジトリを消さずに残していたので、そのまま取り出せました。**書き換えたら作業ディレクトリをすぐ消さないほうがいい**、というのはここで学びました。

Support の窓口の辿り方も書いておきます。同じところで迷う人が居ると思うので。

1. `所有または管理するリポジトリからデータを削除する` を選ぶ
2. `キャッシュされたビューを消去する` を選ぶ
3. アカウントと deployment type（GitHub.com）を選ぶ
4. 製品分野で `リポジトリ` を選ぶ
5. 件名と本文を書く

ここで 1 つ注意があります。**5 のフォームに出てくるラジオボタンで `削除` を選んではいけません。** 選んだ瞬間に「リポジトリの削除に問題がありますか」「削除したいリポジトリの URL は」「リポジトリは一度パージされると復元できません」という、リポジトリ本体を消すための質問群に分岐します。

今回消したいのは PR の中の古い commit であって、リポジトリではありません。ここは `リポジトリの機能` を選んで、追加で出てくる質問には `ブランチ` を選びました。どちらも今回にぴったり合う選択肢ではないのですが、選択肢の側にそういう項目が無いので、いちばん無害なものを選ぶことになります。

実際の依頼内容は本文で伝わりますし、2 で選んだ「キャッシュされたビューを消去する」が URL のパラメータに乗って振り分けに効いています。

ちなみに、フォームを進める途中で GitHub 側の AI が回答を返してきました。要約するとこうです。あなたが求めているのは、履歴書き換えのあとの sensitive data cleanup の documented process に合致している。Support は PR の dereference か削除、サーバー側の gc、キャッシュされたビューの削除ができる。

自分で読んだドキュメントと同じことを言っていたので、そのまま Continue を押しました。

### そのチケットの CC に、消したいアドレスが入っている

チケット作成の最終画面まで来て、思わず声が出ました。

From に現在の開発用アドレスが入っています。ここまでは想定どおりです。その下の CCs に、**今まさに消してくれと頼もうとしている旧アドレスが、既定で入っていました。**

![](https://raw.githubusercontent.com/ishizakahiroshi/qiita-content/main/public/images/05_2026-09-07_git-email-cleanup_illust2.png)

理由は分かります。アカウントに紐づいている検証済みのアドレスなので、連絡先の候補として自動で載っただけです。悪意もバグもありません。

ただ、構図としてはなかなかのものでした。3 時間かけて 23 本のリポジトリから消して回ったアドレスが、その掃除を依頼するフォームの上に、何事もなかったように並んでいる。

x を押して外しました。

ここで学んだのは、**「消した」の範囲を自分で把握していないと、こういうところで漏れる**ということです。Git の履歴からは消えました。でもアカウントに紐づくアドレスとしては、まだ登録されたまま生きています。両者は別の話です。

登録を外すかどうかは、また別の判断になります。今回は外していません。過去に そのアドレスで受けている連絡があるので、外すと届かなくなるからです。ここは掃除の対象ではない、と線を引きました。

### 2 つのセッションが同時に force push しても壊れなかった

これは白状しておきます。

作業を AI コーディングエージェントに任せていて、途中でセッションを 2 つ並行で走らせていました。一方はローカルのフォルダから 18 本を列挙し、もう一方はアカウントから 23 本を列挙しています。両方が、同じリポジトリに対して独立に mirror clone して、書き換えて、force push しました。

普通に考えると事故です。片方の push がもう片方の書き換えを上書きして、履歴が混ざるか、片方の結果が消えるか。

結果としては、壊れませんでした。理由は運ではなく、性質です。

`git filter-repo --mailmap` の書き換えは決定的です。同じ入力（同じ commit グラフ、同じ mailmap）に対して、必ず同じ出力（同じ新 SHA）を返します。commit オブジェクトの中身が同じなら SHA も同じになるからで、これは Git の設計そのものです。

つまり、2 つのセッションは**まったく同じ SHA の履歴を、同じ ref に押していた**ことになります。2 回目の push は 1 回目と同一内容なので、上書きしても何も変わりません。

これは「たまたま無事だった」ではなく、説明できる性質です。ただし成立条件があります。

- 両方が同じ mailmap を使っている
- 両方が同じ時点の GitHub の状態から clone している
- 書き換えの内容が mailmap 置換だけで、パス移動やファイル削除などの別処理が混ざっていない

3 つ目が特に大事で、`--path` や `--invert-paths` を混ぜると、片方だけ処理が違えば当然 SHA がずれます。ずれた状態で両方が force push すれば、後から押したほうが勝って、先に押したほうの結果は消えます。

あと、片方が 18 本、もう片方が 23 本という差があったので、5 本は片方しか押していません。そこは競合していません。

とはいえ、これを狙ってやるのは勧めません。2 波が終わったあとで全 23 本を独立に fresh clone して再検証しました。branch と tag の旧アドレス 0 件、tagger 0 件、`git fsck` の異常 0 件。ここまで確認して、ようやく「大丈夫だった」と言えます。

### ローカルと remote が、共通の祖先を 1 つも持っていなかった

これがいちばん肝が冷えた話です。

ローカルの作業クローンを新しい履歴へ張り替えるときに、1 本だけ様子がおかしいものがありました。ローカルの main が remote の main と噛み合いません。

調べたら、こうなっていました。

- ローカルの main は 33 commit を持っている
- remote の main は 130 commit を持っている
- `git merge-base` が空。つまり共通の祖先が 1 つも無い

まったく別系統の履歴が、同じ `main` という名前で両側に立っていた状態です。おそらく、どこかの時点で GitHub 側だけを大きく作り直したか、別の環境から押し直したのだと思います。ローカルはその前の系統のまま、長いこと fetch していませんでした。

そして、**旧アドレスの commit 11 件は、ローカルの main 側にしか存在していませんでした。** remote 側には 1 件もありません。

もしここで「ローカルにも旧アドレスが残っているから押しておこう」と force push していたら、どうなっていたか。

- 旧アドレスの commit 11 件が GitHub へ再流入する
- remote 側の 130 commit が丸ごと消える

掃除をしに行って、汚して、しかも既存を消す。最悪の手です。

助かったのは、張り替えの判定を「ローカルの branch が upstream より進んでいるか」ではなく、**「ローカルの tip の tree と upstream の tip の tree が一致するか、かつ commit 数が一致するか」**で書いていたからでした。

書き換え後は SHA が全部変わるので、`git rev-list --count <upstream>..<branch>` は「ローカル固有の commit」を大量に返します。これを「未 push の作業がある」と解釈すると、全部のリポジトリが張り替え対象から外れてしまう。逆に無条件で `reset --hard` すると、本当に未 push の作業があるリポジトリで作業を消します。

なので、内容で見ます。

```bash
# tree が同じで、commit 数も同じなら、ただの「書き換え前の同じ履歴」
[ "$(git rev-parse "$b^{tree}")" = "$(git rev-parse "$u^{tree}")" ] && \
[ "$(git rev-list --count "$b")" = "$(git rev-list --count "$u")" ]
```

これが一致するときだけ branch のポインタを動かしました。一致しないものは触らずに理由を出力させています。その出力の中に「tree が違う、commit 数が 33 と 130」というものが混ざっていたので気づけました。

**push の前に `git merge-base` が空でないことを見る。** これは今後のチェックリストに入れます。空なら、そこにあるのは同名の別物です。

```bash
git fetch origin
git merge-base main origin/main   # 何も出なければ共通の祖先が無い
```

ちなみにこのリポジトリ、archive 済みでもありました。つまり今のところ push そのものができません。危ない操作が物理的に塞がれているという意味では助かっていますが、それは結果論です。

ローカル側には、remote に無い変更が 2 commit ぶん載っていました。これは新しいアドレスで作られていて、内容としては残したいものです。ただ、remote 側の同名ファイルとぶつかります。rebase を試したら、案の定 conflict になりました。

ここは今回の作業範囲ではないので、元の状態へ戻して保留にしています。**どちらを正本にするかを決めるのが先**で、決めないまま片方を押すのがいちばん危ない。掃除のついでに決めていい話ではありませんでした。

「作業中に見つけた別の問題を、その場で直さない」というのは、履歴書き換えのように戻せない作業では特に効きます。方針に「メールアドレス整理以外の変更は最小限にする」と書いておいたのが、ここで効きました。

### バックアップは「消える場所」に置かない

最後にこれです。

作業用のディレクトリとバックアップを、セッション用の一時領域に作っていました。作業が終われば消える場所です。

書き換えが全部終わって、検証も通って、それで気づきました。**この一時領域が消えたら、旧 SHA を持つ履歴はどこにも無くなります。** GitHub 側はもう新しい履歴に置き換わっています。

慌てて永続領域へ複製しました。23 本ぶんの mirror clone で 710 MB です。

複製したあとに 2 つ確認しています。

- 全 23 本で `git fsck` の異常が 0 件であること
- **旧アドレスが実際に入っていること**

2 つ目が大事です。「バックアップを取った」と言いながら、中身が書き換え後のものだったら意味がありません。旧アドレスが 1 件以上見つかって初めて、それは書き換え前のコピーです。

復元できるかを確かめていないバックアップは、バックアップではありません。ファイルサイズだけ見て安心しないほうがいいです。

### そして、バックアップが 4 セットに増えていた

並行で 2 セッション動かしていたので、バックアップも別々に取られていました。気づいたら 4 セット、合計 1.4 GB です。

- 書き換え前の mirror（23 本）
- 書き換え前の mirror（18 本）
- 書き換え後の mirror（18 本）
- ローカルの branch 位置を保存した bundle（17 本）

多ければ安心かというと逆で、どれが何なのか分からなくなります。復元するときに間違ったセットを掴んだら、それは復元ではなく上書きです。

整理の基準はこう置きました。**「それが失われたときに、他から作り直せないか」**です。

18 本の書き換え前 mirror は、23 本のほうの部分集合でした。作り直せます。消しました。

書き換え後の mirror は、GitHub 上の現物と同じ内容です。いつでも clone できます。消しました。

bundle は内容が別物でした。ローカルの branch がどこを指していたかの記録で、他のどこにもありません。ただ、該当のブランチと reflog はローカルのリポジトリ側にそのまま残っています。これも消しました。

残したのは 23 本の書き換え前 mirror だけです。1.4 GB が 710 MB になりました。

この判断は自分ひとりで決めずに、消す前に一覧を出して確認を取っています。バックアップを消す操作は、バックアップを取る操作より慎重にやるべきだと思っています。

### なぜ「2 回目の force push」を避けたかったのか

数える工程を丁寧にやったのは、force push を 1 回で終わらせたかったからです。

force push を打つたびに、全部の SHA が変わります。変わるということは、

- 手元の作業クローンが毎回すべて張り替えになる
- 誰かがその間に clone していたら、その人の手元と噛み合わなくなる
- 到達不能になった commit の山が、GitHub 側に毎回積み上がる
- Support への削除依頼が必要な範囲が、そのたびに広がる

3 つ目と 4 つ目が地味に効きます。到達不能な commit は gc が回るまで SHA 直リンクで生きているので、押し直すたびに「消し損ねた履歴」の層が増えていく計算になります。

だから、押す前に全部数える。数えるのはコマンド 5 本で、5 分もかかりません。押し直すほうが圧倒的に高くつきます。

## 何をもって「終わった」としたか

検証は全 23 本を fresh clone してやり直しました。作業に使ったディレクトリで数えると、自分の書き換えの結果をそのまま読んでいるだけになるからです。GitHub から取り直して初めて「向こうがどうなっているか」が分かります。

見たのは 6 つです。

- branch と tag に旧アドレスが 0 件（`git log --all` と `for-each-ref` の tagger）
- `git fsck` の error / missing / broken が 0 件
- commit の `.patch` に旧アドレスが出ないこと（3 本で確認）
- releases と tags の本数が書き換え前後で一致すること
- GitHub Actions が全リポジトリで再有効化されていること、当日トリガーされた run が 0 件であること
- fresh clone して新しい commit を作れること

4 つ目は、タグを押し直したことで Release が壊れていないかの確認です。GitHub の Release はタグ名に紐づくので、タグの指す commit が変わっても Release 自体は残ります。理屈では大丈夫なのですが、理屈で大丈夫なことと実際に大丈夫なことは別なので、Release とタグを持っている 8 本で数え直しました。

Release の本数とタグの本数のペアで、こうなりました。

- 6 / 8
- 2 / 2
- 6 / 6
- 1 / 1
- 14 / 15
- 7 / 7
- 2 / 2
- 6 / 6

書き換え前と全部一致しています。Release を作らずにタグだけ打ってあるものがあるので、ペアが揃っていない行がありますが、それは元からです。

資産（バイナリやアーカイブ）も消えていません。Release に添付したファイルは commit とは別に保管されているので、履歴を書き換えても影響しません。

6 つ目は地味ですが要ります。履歴が壊れていれば、clone した先で commit を作った時点で何か言ってきます。何も言わずに通ることを見ておく。

![](https://raw.githubusercontent.com/ishizakahiroshi/qiita-content/main/public/images/06_2026-09-07_git-email-cleanup_fig2.png)

図の右側が、今回の作業では消えなかった領域です。

## 消えていないものを、正直に書きます

「全部消しました」とは書けません。残っているものが 4 つあります。

**1. `refs/pull` に残っている 3 リポジトリ。** closed / merged 済み PR の head ref です。git からは触れません。PR ページの commit 一覧と `.patch` からは今も読めます。GitHub Support へ削除依頼を出しましたが、**この記事を書いている時点では回答待ちです。** 消えたとは書けません。依頼中です。

**2. fork network。** fork していたリポジトリに旧アドレスの commit が 1 件ありました。該当ブランチは削除しましたが、fork network の性質上、SHA を直接指定すれば上流の URL からたどれます。上流の既定ブランチには入っていないので、普通に閲覧していて出てくることはありません。ここは方針の「割り切る範囲」に入れました。

**3. ローカル専用のブランチ。** remote に無いローカルブランチは、旧履歴のまま残しています。公開されていないので急ぎではありませんが、**将来これを push すると旧アドレスが再流入します。** バックアップ用に切ったブランチ、エージェントが作業用に切ったブランチ、そういうものが積もっていました。

**4. 第三者が既に取得したコピー。** clone、fork、検索エンジンのキャッシュ、Web Archive、取得済みの `.patch`。これは最初から目的に入れていません。

3 番は自分で片付けられるので、いずれやります。1 番は Support 次第です。2 番と 4 番は、もう自分の手の届く範囲にありません。

「公開履歴を整理する」というのは、そういう作業です。**過去に出たものを無かったことにはできません。今後たどれる場所を減らすだけです。**

### force push したあと、GitHub の中はどうなっているのか

ここは理解しておいたほうがいいです。

`git push --force` は、リモートの ref を新しい commit に向け直します。それだけです。**古い commit が消えるわけではありません。**

ref から到達できなくなった commit は「到達不能」になりますが、オブジェクトとしてはサーバー側に残ります。ローカルの git なら `git gc` が回ったときに回収されますが、GitHub 側の gc がいつ回るかはこちらから制御できません。

その間、古い SHA を知っている人は、URL を直接叩けば読めます。

```text
https://github.com/<owner>/<repo>/commit/<古い sha>
```

さらに、その commit が PR に紐づいていた場合は `refs/pull` から到達できるので、そもそも到達不能ですらありません。PR ページを開けば普通に出てきます。

だから公式ドキュメントは、force push で終わりにせず Support に連絡しろと書いています。「cached views and references to the sensitive data in pull requests」を消せるのは向こう側だけだからです。

自分の場合、この構造を理解していなかったら、force push が全部通った時点で「終わった」と書いていたはずです。実際、fresh clone して数え直すまで気づいていませんでした。

**検証を作業ディレクトリでやらない**というのは、こういうときに効きます。自分が押した結果を自分で読み返しても、押していない領域は見えません。

### collaborator が居る場合は、この記事の話は通用しません

念のため書いておきます。今回の条件は「自分が単独の所有者で、collaborator が居ない」です。

他の人が clone している状態で force push すると、その人の手元は次の `git pull` で壊れます。正確には壊れませんが、merge か rebase を強いられて、しかも同じ内容の commit が二重に見える状態になります。ブランチを切って作業していた人は、それを新しい履歴の上に載せ直さないといけません。

公開しているだけで star が付いている程度なら影響は小さいですが、実際に PR を受けているリポジトリなら事前の告知が要ります。そのぶん「いつやるか」の調整が入るので、今日の午前中に片付ける、という進め方はできません。

自分は個人の公開リポジトリだけだったので、その調整が要りませんでした。ここは条件がよかっただけです。

## まとめ

やったことをもう一度並べます。

- 数える。commit の author / committer、ファイル内容の全 ref 走査、code search、gist、タグの tagger の 5 か所
- 方針を先に文章にする。目的、割り切る範囲、許容すること、やらないこと
- mirror clone でバックアップを取り、それをコピーして作業する
- `git filter-repo --mailmap` で置換する。author / committer / tagger が同時に片付く
- push の前に Actions を止め、直後に元へ戻す
- archive 済みは一時解除して押し、すぐ戻す
- fresh clone で検証する。作業ディレクトリで数えない
- 残ったものを正直に書き出す

再発防止の設定については、`Block command line pushes that expose my email` を有効にする道もありました。有効にすれば、次から個人アドレスの commit は push の時点で止まります。

自分は有効にしませんでした。有効化と「開発用アドレスを名義に使い続けること」が両立しないからです。有効にするなら、commit の名義を `<数字ID>+<ユーザー名>@users.noreply.github.com` へ切り替える必要があります。

開発用のアドレスは公開しているものなので、隠す前提の運用に寄せる意味がありませんでした。ただ、これは「公開してよいアドレスを持っているかどうか」で答えが変わる話です。持っていないなら、noreply へ寄せるほうが安全だと思います。

いちばん残ったのは、**切り替えたと思っていたものが、切り替わっていなかった**という事実のほうでした。

開発用アドレスの初出は 2026-06-21 です。そこで切り替えたつもりでいました。実際には 7 月に 35 件、8 月に 9 件、9 月に 2 件、旧アドレスの commit が入っています。最後の 1 件は掃除の 2 日前です。

`.gitignore` は毎回書きます。書かないとファイルが上がってしまうので、忘れたらすぐ分かるからです。commit の署名は、間違っていても何も起きません。**間違っていることが分からないまま、記録だけが積み上がります。**

`user.email` はリポジトリ単位でも設定できるので、global を直しても効かない経路が残ります。新しいクローン、別のマシン、コンテナの中、自動化の実行環境。どこか 1 つ漏れていれば、そこから入り続けます。

なので、設定を直すことより、**混ざっていないかを定期的に数えるほう**を習慣にします。コマンドは 1 行です。

```bash
git log --all --pretty=format:"%ae" | sort -u
```

出てきたアドレスの一覧を見て、意図しないものが混ざっていないか見る。それだけです。
