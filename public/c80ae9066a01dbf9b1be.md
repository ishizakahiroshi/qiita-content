- CVSSの深刻度だけでは、自社で緊急対応が必要かは決まりません。
- 公開情報の確認、対象資産の調査、報告、対応承認、更新実施を分けて考えます。
- 一般エンジニアが全社監視の責任を自動的に引き受けるのではなく、受け口と責任者を決める方が持続可能です。

時間に合わせて、読み方を選べます。

- 少し忙しい人向け：[5分で読める要約版（個人サイト）](https://ishizakahiroshi.com/articles/2026/2026-11-02_cvss-vulnerability-triage-responsibilities/)
- もっと深掘りしたい人は、このまま本文へどうぞ。

「CVSS 10.0」と書かれたCVEを見つけたとき、エンジニアはどこまで対応すべきでしょうか。

自分の担当サーバーなら調べる。一方、全社の環境まで監視し、チャットで警告し、更新結果まで追いかけるとなると話は変わります。この記事では、公開されたCVEを例に、個人の気づきを組織のセキュリティ対応へつなぐ最小限の流れを整理します。

特定企業の構成・調査結果・報告体制を紹介するものではありません。以下のフローやRACIは、一般化した設計例です。実運用では契約・規程・指揮命令系統を優先してください。

## 最初にやるのは「全社通知」ではなく、事実の分解です

今回、判断例として使うのは公開情報の **CVE-2026-112816** です。CanonicalのLXD・MicroCloudで、信頼済みクライアントの公開TLS証明書を用いた認証回避が可能になる問題です。Canonicalは修正版を公表しています。

参考：

- [Canonicalの公式アドバイザリ](https://discourse.ubuntu.com/t/security-advisory-critical-vulnerability-found-in-canonical-lxd-and-microcloud/90557)
- [Ubuntu公式のCVEページ](https://ubuntu.com/security/CVE-2026-112816)

この事例は、「CVSSが高い」「Linuxで利用されるソフトウェア」「公開サーバーを運用している」という断片を雑につなげると、対象範囲を広げすぎてしまうことを示します。

### このCVEについて確認できる事実

| 項目 | 公開情報に基づく説明 |
|---|---|
| 製品 | Canonical LXD、関連するMicroCloud |
| 問題 | HTTPS管理APIのTLSクライアント証明書検証に不備 |
| 攻撃に関係する条件 | APIへ到達でき、信頼済みクライアントの公開証明書を利用できること |
| 想定影響 | なりすまし先の権限次第で管理基盤、ホストに重大な影響 |
| CVSS v4.0 | Canonical登録の基本値は10.0（Critical） |
| 修正 | CanonicalはLXD・MicroCloudの修正版snapを公表 |

ここから直ちに「UbuntuのすべてのVPSが脆弱」とは言えません。LXDが導入されているか、対象バージョンか、管理APIがどう設定されているかが別途必要です。

管理APIが直接インターネットに公開されていなくても、内部ネットワークやリバースプロキシ経由、信頼関係などを確認する余地があります。単に「8443番が閉じている」だけを安全判定の根拠にしないようにします。

![CVEの対象製品と実際の環境を分離するイメージ](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/4423880/6cdc61f0-6c53-41d0-a228-3ef1585f0e3f.png)

## CVSS 10.0と自社リスクを、同じ数字だと思わない

CVSSの基本値は、脆弱性の技術的な深刻度を示す指標です。実際の環境でどれだけ優先して対処すべきかを単独で保証するものではありません。

FIRSTのCVSS v4.0 User Guideでも、Base Scoreは「深刻度」を測り、組織固有のリスク評価には脅威情報と環境情報の補足が必要だと明記されています。

出典：[FIRST「CVSS v4.0 User Guide」](https://www.first.org/cvss/user-guide)

調査時には、少なくとも以下を分けます。

| 軸 | 確認したいこと |
|---|---|
| 深刻度 | 成功時に何が起こるか。CVSSやベンダー説明 |
| 該当性 | 対象ソフトが導入され、脆弱な版・設定なのか |
| 到達性 | どのネットワークや利用者から攻撃経路に届くか |
| 悪用状況 | 実際の悪用、PoC、攻撃の観測情報はあるか |
| 事業影響 | 侵害されたとき何が止まり、何が漏れるか |
| 対応可能性 | 修正版、緩和策、停止リスク、変更承認はどうか |

例えば、CVSS 10.0でも対象製品自体が未導入なら、そのCVEを理由にそのホストを更新する必要はありません。一方、スコアが低くても、外部公開している重要システムに実害があり、悪用が確認されているなら、優先順位は上がり得ます。

大切なのは「10.0なら即、全社に一斉通知」という短絡を避けることです。ただし、**未確認を対象外と扱うのも同じくらい危険**です。

## 個人が動く範囲を、6つの工程に分けておく

NIST SP 800-40 Rev.4は、組織的なパッチ管理を、識別・優先順位付け・取得・適用・適用確認を含むプロセスとして説明しています。

出典：[NIST SP 800-40 Rev.4](https://csrc.nist.gov/pubs/sp/800/40/r4/final)

この考え方を、CVEを見つけた現場のエンジニア向けに小さくすると、次の6工程にできます。

1. 一次ソースを確認する。CVE番号、ベンダー、影響条件、修正状況を押さえる。
2. 自分の担当資産と突き合わせる。管理台帳と導入済みソフトウェアを確認する。
3. 該当性・到達性・事業影響を分けて評価する。不明点は未確認にする。
4. 自分の権限で判断できない事項を担当者に渡す。連絡先と受領者を記録する。
5. 変更は承認と運用手順に従って行う。公開サービスなら停止・ロールバック条件を検討する。
6. 実施結果と残ったリスクを記録し、必要な関係者へ完了・継続調査を通知する。

![脆弱性の受け取りから検証までを示す6工程のフロー](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/4423880/2d5c7a95-b5d4-4b8d-9cdf-ec9140902efa.png)

このうち「公開情報をたまたま見つけた人」が全工程の責任者になる必要はありません。役割が正式に与えられていないなら、少なくとも **発見者と、対応を決定する責任者を区別する** ことが必要です。

## 資産の有無を確認するなら、まず読み取り専用で

CVE-2026-112816を例に、UbuntuのホストでLXD・MicroCloudの導入を初期確認するなら、snapとAPTの双方を確認する方法があります。

以下は影響判定を完了させるスクリプトではなく、**調査の入り口となる読み取り専用の例**です。

```bash
# snap で管理されている対象製品を一覧から探す
snap list 2>/dev/null | awk 'NR == 1 || $1 == "lxd" || $1 == "microcloud"'

# APT パッケージとしての導入を確認する
dpkg-query -W -f='${binary:Package} ${Version}\n' lxd microcloud 2>/dev/null || true

# 関連する systemd ユニットの存在を確認する
systemctl list-units --all 'snap.lxd*' 'snap.microcloud*'
```

何も見つからなくても、手動導入・別の配布方式・コンテナ内の入れ子構成までは否定できません。クラウド事業者が提供するVPSのホスト側仮想化も、ゲストOS内でコマンドを実行しただけでは完全に把握できません。

「snapにないので対象外」と書かず、「snap版は見つからなかった。ほかの導入経路は未確認」と記録します。

なお、実際に脆弱なLXD・MicroCloudを使っている場合、Canonicalは速やかな更新を勧めています。ただし配布元やクラスタ構成で更新手順が変わるため、**一般記事に掲載した一律の更新コマンドを本番へそのまま投入することは推奨しません**。

## 発見、調査、承認、実施をRACIで切り分ける

ここで役立つのがRACIです。Rは作業実行、Aは結果に対して説明責任を持つ担当、Cは相談先、Iは情報共有先を表します。以下は小規模組織の考え方を整理するための一例であり、法的な義務や既存の社内権限を決める表ではありません。

| 工程 | 発見者 | システム運用担当 | セキュリティ調整担当 | 責任者・決裁者 |
|---|---|---|---|---|
| 公開情報の初報 | R | I | A | I |
| 対象資産との照合 | C | R | A | I |
| 対応優先度・方針 | C | C | R | A |
| 更新・緩和策の実施 | I | R | C | A |
| 結果の確認・記録 | I | R | A | I |

上の表は、発見者が偶然担当運用者だった場合には同一人物が複数の列を兼ねることもあります。小規模な組織なら、セキュリティ調整担当と責任者を兼任する場合もあります。

問題は、役職名の数ではありません。**誰もAを引き受けていない状態**と、**Aが明確にならないまま発見者に仕事だけ積み上がる状態**です。

NIST CSF 2.0のGV.RRは、役割・責任・権限の確立と共有を求めています。国内でもIPAが、役割や責任の範囲を定めることを推奨しています。

- [NIST CSF 2.0](https://www.nist.gov/publications/nist-cybersecurity-framework-csf-20)
- [IPA「サイバーセキュリティリスク管理体制の構築」](https://www.ipa.go.jp/security/economics/practices_navi/practice204.html)

## 通知が必要なときは「危ないです」だけで終わらせない

全社チャットで一件ずつCVEを共有すると、受け手は「結局、何をすればいいのか」が分からなくなります。

代わりに、初報の段階を次のいずれかとして明示すると、誤解を減らせます。

- **対象外**：対象資産が存在しないことを確認できた。確認範囲を明記する。
- **未確認**：資産の有無、バージョン、公開設定などに不足がある。
- **要調査**：対象製品はあるが、影響条件や到達性が未確定。
- **要対応**：影響が確認され、対応の担当者・期限・方法を決める必要がある。
- **対応済み**：更新または緩和策が適用され、検証まで終わった。

例えば、運用担当が上司へ共有する初報なら、この程度で十分です。

```text
件名：対象ソフトウェアの脆弱性確認
情報源：ベンダー公式アドバイザリ（URL）
対象：担当システムのうち確認した範囲
現状：対象製品の有無は未確認
危険性：成立条件と想定影響を簡潔に記載
依頼：資産確認の担当と期限の決定
次回報告：確認結果がそろい次第
```

これは「自分が全部直します」という宣言ではありません。「ここまで分かっていて、ここからは判断が必要です」という引き継ぎです。

逆に、具体的な侵害の兆候や攻撃の進行を把握した場合は、このような通常の脆弱性トリアージではなく、組織のインシデント対応手順に従って速やかに連絡します。黙って自分の担当範囲だけを見る、という話ではありません。

## 「外と通信できないから安全」にも、ひと呼吸置く

担当外のシステムへの影響を考えるとき、ネットワークの分離は有力な材料です。ただし、「相手からこちらへ接続できない」だけでは、完全な隔離を意味しません。

確認したいのは、通信ポートだけではありません。

- こちらから相手への接続や自動連携はないか。
- 共通の認証基盤、管理アカウント、秘密情報の保管場所はないか。
- ファイル共有、バックアップ、CI/CDなどの信頼関係はないか。
- 障害や侵害が波及する業務上の依存関係はないか。

とはいえ、これらを全社規模で棚卸しする仕事まで、一人の発見者が背負うのは無理があります。**担当環境への依存関係が疑われるところまでを報告し、判断権限が必要な調査は引き継ぐ**。その境界が実務的です。

## 自動化するならCVE監視より、まず資産の一覧から

「毎日重大CVEだけ通知するbot」を作るのは比較的簡単です。でも、対象資産が分からなければ、botは毎日「危険かもしれません」と言い続けるだけになります。

先に必要なのは、小さくても正確な資産台帳です。

```yaml
# 個別の会社・サーバーを表さない項目例
asset:
  owner_role: service-operator
  os_family: linux
  software_inventory_status: verified
  last_verified: "YYYY-MM-DD"
security_process:
  intake_role: security-coordinator
  decision_role: service-owner
  change_approval_required: true
  unresolved_status: unknown
```

`owner_role`が分かるだけでも、通知の行き先が変わります。製品名・バージョンの一覧、更新の責任者、最終確認時点がそろえば、CVSSのニュースを「自社に関係する課題」に変換しやすくなります。

ただし、この例は自動判定の完成形ではありません。手動導入の見落とし、更新後の稼働状態、API公開設定などは別途確認が必要です。

## では、報告しない選択はどこまで許されるのか

ここは技術論だけでは決まりません。職務範囲、就業規則、委任された権限、実際に把握した危険の切迫度によって、求められる行動は変わります。法律上の義務を一律に断定するつもりもありません。

少なくとも「公開CVEを一件見つけた」という事実と、「会社全体の全資産を調査し、更新を完了させる責任」は別です。

一方、担当システムに重大な脆弱性があると具体的に確認したのに、何もせず放置するのは適切ではありません。担当外でも事故や重大な危険を具体的に認識したなら、決められた連絡経路で共有すべきです。

だから、次の区別が必要だと思います。

- 公開情報だけを知った：一次情報と担当範囲の関係を確認する。
- 自分の担当資産に該当すると分かった：担当業務として判断者に報告し、対応を進める。
- 担当外に具体的な重大リスクを見つけた：所管の担当者や窓口へ事実を渡す。
- 社内の網羅的な監視：正式な責任分担、工数、対象範囲を組織で決める。

「すべて報告する」でも「何も知らせない」でもない、中間の運用です。

## 小さな現場ほど、責任の受け皿を先に決めたい

IPAの実践資料には、専任セキュリティ部門を作れない組織向けの兼任体制の例もあります。立派なSOCやCSIRTをすぐ整備することが唯一の道ではありません。

出典：[IPA「兼任のサイバーセキュリティ管理体制の構築」](https://www.ipa.go.jp/security/economics/practices_navi/practice205.html)

例えば、最低限決めておきたいのは、脆弱性情報の受け口、資産ごとの運用担当者、更新の承認者、緊急時の連絡先です。

その四つさえ決まっていれば、最初の発見者は「この情報は誰へ渡せばいいか」で悩まずに済みます。

別に「今後はセキュリティの話をしません」と宣言する必要もありません。普通に自分の担当環境を見て、具体的な影響を見つけたら報告する。組織的な監視が必要なら、その仕事として範囲を定める。

善意の情報共有が、いつの間にか無期限の当番になるのは避けたいところです。

![一人が抱える警告を、定義された役割へ手渡す場面を抽象化した図](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/4423880/4a7fbdf0-0ab2-4f01-a00e-e833e5c79fd4.png)

## まとめ：発見者が全工程を抱えなくていい設計にする

技術者としての調査は、続けたいです。脆弱性が公開されたとき、自分が持っている環境に関係するかを確認し、危険があれば必要な対応をする。そこには納得があります。

一方、何かを知っただけで、いつの間にか会社全体の監視担当になるのは、持続可能ではありません。

CVEを見つけること、影響を判断すること、更新を決めること、実施して検証すること。いったん分けて、適切な人が受け取れるようにしておく。

明日また重大なCVEが出ても、まず対象資産との関係を確認するところから始めます。
